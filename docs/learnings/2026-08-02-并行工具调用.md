# 并行工具调用：Responses API 的单轮多 function_call

## 核心原理

OpenAI Responses 的 function calling 是一个**显式续接协议**：

1. 请求里下发 `tools` schema，模型在响应里返回 `function_call` item（每个带唯一 `call_id`）。
2. 业务代码执行工具后，必须把结果作为 `function_call_output` item 回传，且**必须带上同一个 `call_id`**。
3. 模型根据所有输出继续决策，直到不再调用工具、直接输出最终答案。

`parallel_tool_calls=true` 只影响第 1 步：模型可以一次返回多个 `function_call`。但第 2 步有一个硬约束——
**同一批 `function_call` 的输出必须一起提交**：不能执行一半就发下一个请求，否则协议断裂。

## 关键设计决策

### 1. 模型 items 每轮只追加一次，output 按 call 追加
Lucas 显式持有上下文（不用 `previous_response_id`），所以本轮 `response.output` 里的
message/function_call/reasoning items 只追加一次，随后对每个 call 单独追加
`function_call_output`。顺序必须是「所有 function_call → 所有 output」，模型靠 call_id 配对，
不靠位置。

同一批调用按「只读并行、写入串行」执行（见下方第 5 点）：只读调用用 `asyncio.gather`
并发执行，写入调用按模型发出顺序逐个 `await` 串行执行。执行前先把整批 `tool_start`
事件广播给前端，前端才能同时展示所有并行工具的进行中状态；两类结果按原调用顺序合并
逐个回传，观测截断配额与停滞检测保持确定性。

### 2. 单轮上限（MAX_PARALLEL_TOOL_CALLS=4）
并行是给模型的自由度，不是无限自由度。上限防止模型一次发十几个调用造成失控（成本、权限、
trace 都变难收束）。超出上限仍走「协议错误 + 有界纠正」路径（最多 3 次）。

### 3. 部分失败语义：全部结果照常回传
并行轮里一个调用失败（如越界被拒、参数非法），不整轮拒绝——失败结果作为该 call 的
`function_call_output` 回传，让模型看到「哪个成功、哪个失败」后自己决定重试或换方案。
这与单工具时代的失败处理一致。

### 4. 状态跟踪要按维度拆分
单工具时代很多状态是「全局单值」，并行后必须拆：
- 失败签名从「全局最近一次失败」改为「按 tool 记录最近失败」，否则并行轮里
  「A 失败、B 成功」会把 A 的失败记录清掉。
- 停滞检测（相同结果重复出现）要排除同一并行轮内的重复——两个并行调用返回相同结果时，
  模型还没机会看到结果，不能算「无进展」。

### 5. 只读并行、写入串行（2026-08-09 修正）
最初实现把同批所有调用（含写入）一起 `asyncio.gather` 并发执行。真实任务里模型会把
多个 `apply_patch`/`write_file` 放进同一轮（例如同一文件多处修改），并发写会竞争
同一文件状态，结果不确定。修正为 `ToolSpec.parallelizable` 显式标记：只读类工具标记
`parallelizable=True` 仍并发，未标记的写入调用（`write_file`/`apply_patch`/`update_plan`）
在只读调用之后按模型发出顺序逐个执行，输出仍按原顺序一起回传（Responses 协议不变）。

取舍：写入串行损失少量吞吐，换取同文件写入的确定性与安全性；同批内顺序固定为
「先读后写」，写后读属于依赖关系，仍需模型拆轮（协议纠正不变）；默认不可并行
（fail-safe），新工具未标记即串行。

## 取舍

- **收益**：多独立查询任务少走模型轮次（MULTI-01 单轮读完 4 个文件），消除「合法多 call
  被协议错误纠正」的失败模式；DeepSeek 在 `parallel_tool_calls=false` 下仍会偶发多 call，
  旧 Runner 只能拒绝，新 Runner 能正常执行。
- **代价**：并发执行多个工具时，观测截断配额、trace 事件、step 语义都要从「单调用」想成
  「单模型轮 = 多个调用」；前端 summary/工具行按 step+tool 区分展示。
- **验证**：真实模型 3/3 稳定并行 4 调用；LOOP-01（反复检索护栏）无回归。

## 一句话总结

并行工具调用的本质不是「多线程执行」，而是**协议层的多 call 批量续接**：把
「单轮单 call + 拒绝纠正」改成「单轮多 call + 全部输出一起回传 + 上限保护」，
同时把失败/停滞等状态跟踪从全局单值拆成按维度独立记录。
