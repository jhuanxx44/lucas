# 分级链式上下文压缩：低损丢弃 → LLM 摘要 → 有损兜底

日期：2026-08-01
对应实现：`harness/runner.py` 的 `compress_context` 三级链式改造，
规划见 `docs/plans/2026-08-01-context-management-v1.md`。

## 一、核心原理：压缩不是一种动作，是一条按信息价值分级的链

上下文超预算时，不同内容的「可丢弃性」不同，压缩手段也应该分级，而不是一刀切：

1. **低价值丢弃**（成本 0）：更早步骤的 reasoning 草稿、工具轮的中间 assistant 叙述。
   这类内容不承载任务关键事实，丢了对成功率几乎无影响，先丢还能缩小后续摘要的输入。
2. **LLM 摘要**（成本 1 次普通模型调用）：最早可压缩步骤的 tool output 与关键消息。
   这是「理解 + 重写」：模型先把原始内容浓缩成交接摘要，再整体替换这些步骤，
   取代了原来「占位挖空」的机械做法。
3. **有损机械兜底**（成本 0，信息损失最大）：软线仍超则逐条丢 assistant 消息，
   硬线（0.95×窗口）则从最早步骤整轮 FIFO。只在摘要仍解决不了时使用。

每级之后重估预算，够用就停。`compression_level=1`（实验 baseline）只走
1(仅 reasoning)+占位挖空+3，与旧版逐字节一致；`compression_level=2`（默认 max）走完整链。

## 二、关键设计决策与取舍

### 1. 为什么「先占位挖空再摘要」是错的

占位挖空会把 tool output 替换成「结果已丢弃」的固定文案，摘要模型再聪明也
无法从中恢复事实。所以链式模式里，**tool output 必须让摘要直接看到原始版本**；
第 1 级只丢摘要不关心的 reasoning/中间叙述。这决定了链的顺序不是任意的：
机械在前只能丢「无需摘要」的内容，「需要浓缩」的内容必须先给摘要。

### 2. 摘要请求本身也要放得进窗口

摘要调用是独立请求，输入是「被覆盖内容的原始文本 + 摘要 prompt」。输入上限按
`窗口 × 0.8 / 校准系数` 折算（约窗口 80% 的 token），既保证摘要请求不会超窗，
又允许覆盖接近满窗的大输出。单步超过上限时跳过该步，留给第 3 级兜底
（对齐 Codex `build_compacted_history_with_limit` 对摘要输入做截断的思路）。

### 3. 摘要失败必须可降级

摘要调用失败（超时/网络/协议错误）不能中断整个 run：降级为对该批步骤做占位挖空
（与 level=1 同款），并记录 `degraded`。这是 Lucas 相比 Codex 的有意差异——
Codex 压缩失败会中止 turn，Lucas 有已验证的机械路径兜底，产品闭环更平滑。

### 4. 协议结构红线

Responses 协议要求 `function_call` 与 `function_call_output` 按 call_id 成对。
摘要替换的是**整步**（assistant 消息 + call + output 一起进摘要输入），
不会出现只有 output 没有 call 的半截结构；占位降级同理（保留 item 只改 output 文本）。
已生成的摘要消息带 `⚠️ [上下文摘要]` 前缀，后续压缩跳过，避免被再次摘要。

### 5. 硬线的角色变化

硬线不再是「FIFO 丢记忆」的唯一手段，而是整条链的终结点：软线触发后先低损丢弃、
再 LLM 摘要，摘要解决不了才 FIFO；初始预估即超硬线时仍拦截不提交必败请求。
信息该保就保，机械删除只作为最后手段。

## 三、实现要点（踩过的坑）

1. **摘要调用的输入上限不能拍脑袋定死**：最初用固定字符上限，导致大输出步骤
   永远无法被摘要覆盖、整条链空转（`compress_context` 返回 None，一次都不压）。
   改成按窗口比例（0.8×窗口/系数）后，大输出才能进摘要输入。
2. **校准系数异常会缩小摘要输入预算**：测试里假 usage 让字符→token 系数偏离，
   摘要输入上限随之缩小。实现上系数只来自真实 API usage 的正增量，生产不受影响；
   测试要意识到窗口上限与系数联动。
3. **摘要调用必须计入 usage/成本**：`_merge_usage` 把摘要 turn 的 usage 并入
   全 run 累计，否则 trace 里 token/成本少算一次调用。
4. **事件分级**：`context_compressed` 事件新增 `level`、`chain`、`degraded`，
   `context_summarized` 记录覆盖步与前后规模，eval 可以按级归因哪一级起了作用。
