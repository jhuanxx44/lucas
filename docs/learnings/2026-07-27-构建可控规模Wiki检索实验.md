# 怎样构建一个可控规模的 Wiki 检索实验

比较检索算法最难的部分通常不是写 TF-IDF 或 BM25，而是让“知识库大小”成为唯一变化的变量。如果 50 页库和 500 页库里的相关文档也不同，指标变化可能只是因为答案后来才进入知识库，不能归因于排序算法。

本次采用冻结母库加 manifest 的方法。先从真实网页抓取 500 篇来源快照，再由 LLM 只根据快照整理页面。冻结后不再让 trial 修改母库；每次实验用 manifest 把指定页面复制进独立 workspace，并重建当前可见的 index。这样 Agent 看不到母库其余路径、标题或缓存。

实验分成两条轨道。受控干扰轨道始终保留问题的全部相关页面，规模从 50 增加到 500 时只加入干扰文档，适合回答“噪声变多会怎样”。自然增长轨道允许答案随知识库一起进入，适合模拟产品增长，但它的改善不能解释为排序变好。

知识库质量也必须先于检索实验。真实 URL 不等于事实可靠：本次 10% 分层抽检发现日期换算、速率口径和人物身份等错误。如果不先修正，这些错误会同时污染查询、ground truth 和最终答案，看起来指标完整，实际是在测一套自洽的错误。

相关性标注也不能只把“生成问题时使用的页面”当成唯一答案。新库中可能还有同主题页面。本次先合并两个检索器的 Top-20，再加入同领域和随机文档，标注 0–3 级相关性。受控子库保留所有 grade≥2 的页面，避免扩库后漏标把正确召回判成错误。

最后要区分三个层次：排序公式、可部署工具、Agent outcome。共享表示时 TF-IDF 可以优于 BM25，但把生产子串 BM25 机械改成子串 TF-IDF 可能更差；即使离线排名更好，Agent 仍可能只召回一半证据或引用错误路径。只有 test 指标和多 trial outcome 都稳定改善，才有理由切生产实现。

查询输入也必须与生产契约一致。生产 `wiki_recall` 已删除自然语言分词路径，只接受 Agent 生成的预分词关键词。因此离线实验先用同一模型生成并冻结关键词缓存：纯公式对照可对关键词再做共享 tokenizer 以隔离公式差异，而生产形态对照必须直接使用原始关键词短语。拿自然语言问句经 jieba 得到的结果，不能代表当前产品链路。

这套方法的核心不是追求一个漂亮分数，而是让每个结论都能回答：改了哪个变量、证据来自哪里、在哪个规模有效、是否真的传导到了最终任务。
