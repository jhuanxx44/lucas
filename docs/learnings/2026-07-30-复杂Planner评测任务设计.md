# 如何设计能测出 Planner 价值的复杂 Agent 任务

## 问题

早期 `planner-experiment-v1` 的 4 个任务全部通过，但 12 次运行中模型一次也没有调用
`update_plan`。这说明原任务的线性路径已经足够清楚，只能验证工具和 Runner 可用，不能区分
“有 Planner”和“没有 Planner”。

本轮新增 `PLAN-01`～`PLAN-03`，目标不是让 Agent 表演规划，而是提供三个可能让规划产生
实际收益的固定环境。待验证假设是：**面对多阶段依赖、多个最终产物和条件式动作时，显式
Planner 能减少遗漏、串写和计划外修改，并提高环境最终成功率。**

## 三种复杂度

### 1. 依赖顺序

`PLAN-01` 要先从五个服务中筛出三个迁移目标，再更新配置、根据依赖生成部署顺序，并生成
逆序回滚计划。复杂度不来自文件数量本身，而来自“筛选 → 修改 → 拓扑顺序 → 回滚”的依赖。

### 2. 中间产物依赖

`PLAN-02` 要先把三份季度材料分别写回三个公司档案，之后才能生成横向报告，最后再更新索引。
它能暴露数据串公司、只写报告不更新底层档案、遗漏索引和覆盖风险提示等失败。

### 3. 条件式行动

`PLAN-03` 给出指标、日志、发布记录和 runbook。Agent 只能执行证据满足条件的两项处置，必须
明确不修改指标正常的库存系统。这比“照着清单全改”多了一层判断，也能测量 Planner 是否帮助
维护证据、动作和验证之间的对应关系。

## 为什么不强制固定工具路径

三个任务都用最终文件状态和 pytest 判卷。Agent 可以自由选择 `search`、`read_file`、
`apply_patch` 或 `write_file`，也可以不用 Planner。`plan_usage` 是非必需 process 指标，不能
替代环境 outcome。

本轮只新增一个通用 `allowed_diff` safety grader，确保 Agent 不能通过修改题目、测试、来源或
额外文件蒙混过关。它约束的是权限和最终修改范围，不是推理路径。

## 后续对照方式

正式实验应对同一套 `planner-complex-experiment-v1` 运行三组：

1. baseline：不提供 `update_plan`，删除 Planner 专属 prompt 规则；
2. optional Planner：提供 `update_plan`，由模型自行决定是否规划；
3. required Planner：只在这套复杂任务中要求先形成计划，用来测机制潜在收益。

三组固定模型、工具、fixture、预算和 grader。先各跑 3 次检查题目与 trace，再根据失败率把正式
样本提高到每题每组 5～10 次。主要比较 success rate；steps、token、成本、遗漏、返工和 plan
偏离只用于解释结果。如果 Planner 只是增加调用而没有改善 outcome，就不应成为默认机制。
