# Context 压缩实现：提交前预估、动态校准与结构完整

日期：2026-08-01
对应：阶段 1（成本画像后的 token 预算压缩），规划见
`docs/plans/2026-08-01-context-management-v1.md`

## 一、核心原理

### 1. 为什么"提交前预估"，而不是"提交后看 usage"

超窗请求 API 会直接报错，所以必须在提交前知道会不会超。提交前能精确知道的只有：

- 上一轮真实 `prompt_tokens`（API 返回，权威值）；
- 本轮要新增的 items 的**字符数**（自己手里的内容，可精确统计）。

所以预估公式天然是：

```
下一轮 ≈ 上一轮真实 prompt_tokens + 本轮新增字符 × 系数
```

不是把全部历史重新编码一遍，只估增量。

### 2. 为什么不用 tiktoken

- 事后有真实值（`usage.prompt_tokens`），自己算一遍是重复；
- 事前只需要增量粗估，且系数可以用真实数据校准；
- DeepSeek 用自家 tokenizer，tiktoken（OpenAI 词表）算出来反而不准；
- 阈值是 `窗口 × 0.8`，留了 20% 余量，粗估误差无感。

### 3. 动态校准：真实 Δ 就是免费的"tokenizer"

每轮提交后：

```
Δprompt_tokens = 本轮真实 prompt_tokens − 上一轮真实 prompt_tokens
Δchars         = 本轮提交的新增 items 字符数
系数           = 最近几轮 Δtokens / Δchars 的加权平均
```

新增字符是提交前就知道的，新增 token 是提交后 API 免费给的——两组数据一对除，
就得到贴合当前内容分布的字符→token 系数，且自动适应中文/代码/长 JSON 的混合。

## 二、关键设计决策与取舍

### 1. 保留最近一步 + 挖空更早 tool output，而不是整步丢弃

- **保留最近一步全量回放**：模型需要看到最近一次工具结果才能继续决策；
- **更早 tool output 替换为占位说明**，而不是删掉——保持 Responses 协议结构完整
  （`function_call` 与 `function_call_output` 按 call_id 成对），且占位说明明确告诉模型
  "该步骤已执行、结果被压缩丢弃、请勿假设其内容"，防止幻觉引用；
- **assistant 消息（模型判断链）保留**：tool output 通常是最大头，先省它。

取舍：这不是从头截断，前缀不稳定（早期 assistant 消息在、工具结果被挖空），
prefix cache 命中打折——但省 token 更多，第一版接受。

### 2. plan 永不压缩

`update_plan` 的 call 与 output 标记为不可压缩。plan 是任务级状态，任务全程需要
持续可见；丢失会导致模型遗忘计划（路线图 Phase 2 已记录此坑）。它的体积很小
（真实 case 38 次累计 6.7K 字符），全部保留无成本问题。

### 3. reasoning 平时保留、压缩时丢弃

未压缩时 reasoning 作为 API 消息每轮回传（模型可引用自己之前的推理）；
触发压缩时更早步骤的 reasoning 全部丢弃，省 12–18% 的重复成本。

### 4. 兜底：仍超阈值 → 从最早丢弃 assistant 消息

挖空 tool output 后仍超阈值时，按从早到晚的顺序丢 assistant 消息直到不超；
单条 output 超硬上限单独截断（复用现有 `MAX_OBSERVATION_CHARS` 逻辑）。
每次超阈值都触发（可多次压缩），不限制一 run 只压一次。

## 三、UI 表现：一条事件贯穿三层

压缩是后台机制，但触发时用户应可感知、可归因：

- runner 推 `context_compressed` 事件（before/after 预估、释放 token、丢弃 step 列表），
  同时写入 trace；
- 产品聊天链路转发为 SSE `context_compressed`；
- 前端三层表现：输入框 Context 圆环脉冲 + "压缩"徽标 + tooltip 摘要；
  步骤列表新增"上下文压缩：丢弃 N 步工具结果，释放约 X tokens"（随消息持久化、可导出）；
  Trace 事件层保留 dropped_steps 明细。

eval 直跑 runner 时事件只进 trace，无前端表现——UI 不接入实验路径。

## 四、实现要点（踩过的坑）

1. **预估基线用上一轮真实值，压缩要同时算"老 items 的净变化"**：压缩挖空的是已经提交过
   的老 items，下一轮真实 prompt_tokens 会因此下降。预估公式必须为
   `last_real + (新增字符 + 老 items 净变化) × 系数`，否则压缩后以为自己还超阈。
2. **并行数组跟踪 step**：`context.input_items` 是扁平列表，压缩需要知道每个 item 属于
   哪一步、是不是 `update_plan`，所以维护 `item_steps` 平行数组 + `call_id → (tool, step)`
   映射；压缩后原地重建并同步 pending 计数。
3. **校准对只记正增量**：压缩轮 `Δprompt_tokens` 可能为负，跳过该轮，避免污染系数。
4. **未超阈值零行为差异**：`context_window=0` 时整个机制短路，提交内容与 baseline
   逐字节一致——这是回归测试的底线。
