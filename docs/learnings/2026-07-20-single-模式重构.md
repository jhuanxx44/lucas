# Single 模式重构：把两代并存的代码并为一条链路

## 这是什么

Lucas 里曾经同时存在两套 Agent 系统：一套是新的通用运行时 `harness/AgentRunner`（一个模型自己决定"调工具还是回答"的循环），一套是旧的业务流水线 `agents/`（一个经理 Agent 先把问题派发给几个研究员，再汇总）。本次重构删掉了旧的整套系统，让产品聊天、wiki 收录、评估测试全部走同一个 Runner。删了 4135 行旧代码，143 个测试全绿。

这篇教程解释重构背后的四个通用原理，下次遇到类似的大改动可以直接套用。

## 1. 为什么"先建后拆"比直接删安全

直接删旧代码、同时写新代码，最大的风险是**中间状态不可验收**：删了一半发现新链路有坑，旧链路已经拼不回去，进退两难。

这次用的策略叫 **build-then-cut（先建后拆）**：

1. 先把新链路完整建出来（此时新旧并存，旧的还是生产路径，系统始终可用）。
2. 新链路的每个里程碑都有独立的验收标准——M1 验收"测试全绿且 eval 结果与基线一致"，M4 验收"前端零改动完成一次完整问答"，M5 验收"raw 目录逐字节不变的约束测试继续通过"。
3. 全部验收通过后，最后才删旧代码（M6）。

好处有两个：

- **每一步都可回退**。任何一个里程碑失败，停在那里系统也是好的，不会留下"删了一半"的半成品。
- **每一步都可归因**。测试挂了，一定是当前这个小改动引起的，而不是"大改后的某个地方"。

类比：搬家时先把新家收拾好、确认水电都通，再退掉旧房子；而不是先退房再慢慢收拾。

## 2. ReAct 循环里，什么归模型管、什么归代码管

ReAct 循环就是：模型输出一段 JSON（"我要调工具 X，参数是 Y" 或 "我的最终答案是 Z"）→ 代码执行 → 把结果喂回模型 → 重复，直到模型给出答案。

这次重构严格遵守了一条职责划分（也是 AGENTS.md 的硬约束）：

**代码保证"执行语义"**——这些事绝不能靠模型自觉：

- **终止**：步数超过 `max_steps`、花费超过 `max_cost_usd`，代码直接掐停。模型可能永远不想停。
- **熔断与预算**：每次模型调用后累计 token 用量，超预算以 `budget_exceeded` 结构化结束，而不是指望模型省钱。
- **权限**：`allowed_tools` 白名单在代码里检查，模型要求调白名单外的工具会被拒绝。
- **校验**：wiki 写入前的 frontmatter 必填字段检查、更新丢失检测、写前备份，都是确定性代码。

**prompt 只承载"行为策略"**——这些事交给模型判断更好：

- 先查行情还是先搜新闻（工具使用偏好）。
- 答案写成什么风格、什么结构。
- wiki 编译时哪些内容值得保留。

为什么这样分？因为执行语义要求**100% 可靠**，而模型的输出本质是概率性的——让它"尽量别超预算"就像让司机"尽量别超速"，不如直接装限速器。反过来，策略需要灵活性，写死在代码里就失去了用大模型的意义。

## 3. 事件级流式 vs 逐 token 流式的取舍

旧系统的聊天体验是"逐 token 流式"：回答像打字一样一个字一个字蹦出来。新链路目前降级为"事件级流式"：每完成一个工具调用发一条状态，最终答案一次性（或分段）推送。

这不是偷懒，而是 **JSON-per-step 协议的天然约束**：模型每一步的输出必须是一段完整的 JSON（`{"action": "tool", ...}` 或 `{"action": "answer", ...}`），代码拿到完整 JSON 才能解析、才能知道这一步是调工具还是回答。如果边生成边推送，用户会先看到一堆协议外壳（`{"action": "to`...），那是内部实现细节，不是给人看的。

取舍的结论：

- **工具调用阶段**：本来就没有"答案文本"可流，发"正在调用 stock_quote"这样的事件反而信息更清楚。
- **answer 阶段**：模型一旦决定回答就不会再调工具，这部分输出**可以**安全地逐 token 流式推给用户。这是已登记的 backlog，属于锦上添花，不阻塞主链路。

经验：当协议要求"完整消息才能解析"时，流式的粒度天然以"一条完整消息"为界；想更细，就得在协议上为特定阶段开特例，而不是强行流一切。

## 4. wiki 重建："设计思想"带走，"实现细节"丢掉

旧的 wiki 收录模块有 932 行。重写时没有逐行搬运，而是先做了一次"思想提炼"：从旧代码里提炼出 **7 条设计思想**作为新实现必须守住的契约，其余明确标记为"可丢弃"。

**带走的设计思想**（回答"为什么这样设计"）：

1. 四层存储边界：`raw/`（只读）→ `ingested/`（收录）→ `reports/`（归档）→ `wiki/`（编译视图），单向流动，下游可从上游重建。
2. 来源与页面分离：wiki 页面在 frontmatter 里声明"我由哪些来源编译而来"，用声明式溯源代替状态数据库。
3. Plan → Compile 两段式：LLM 先输出"要写哪几页、为什么"的结构化计划，再按计划逐页写作——决策可校验，写作自由。
4. 写入前确定性校验 + 备份。
5. 增量更新：保留旧内容，新增标注日期，新旧矛盾并存标注。
6. 收录两段确认：机器先分类提议，人确认后才落盘。
7. 索引优先召回：先查索引再全文兜底。

**丢掉的实现细节**（只是"当时恰好这么写"）：

- A 股行业列表等硬编码 → 移进 `lucas.yaml` 配置，领域本体不进代码。
- 用字符串拼接维护 index.md → 改为结构化重建。
- 手写 frontmatter 文本扫描 → 统一走 yaml 解析。
- 单份 `.bak` 备份、整页覆盖写 → 本版暂保留，但已登记 backlog（改 patch/event sourcing）。

区分方法很简单：问一句"**如果换一个实现方式，这条约束还应该成立吗？**"——应该成立的是设计思想（如"raw 不可变"换什么实现都成立）；不一定成立的是实现细节（如"用字符串拼接维护索引"显然可以换）。重构时只向前者负责，后者允许自由重写，新代码才能既守住本质又甩掉包袱。
