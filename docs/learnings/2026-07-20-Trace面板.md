# Trace 面板：把 Agent 的执行过程变成可回看的产品数据

## 这次做了什么

Lucas 原来只把工具调用压缩成一句“调用了什么”的状态文案。现在聊天页面右侧增加了可隐藏的 Trace 面板：每轮对话单独分组，能看到 Lucas 的动作、工具名、工具输入和工具输出；执行中的步骤实时出现，完成后跟随助手消息一起保存，因此切换会话或刷新页面后仍能回看。

## 1. 为什么 Trace 应该使用结构化事件

一句 `调用 wiki_recall: 东山精密` 适合给人快速浏览，却无法可靠地还原参数和结果。如果前端再从这句话里解析工具名和参数，文案稍有变化就会失效。

这次让 SSE 直接透传 Runner 已经拥有的结构化 `tool_step`：

```json
{
  "step": 1,
  "tool": "wiki_recall",
  "args": {"query": "东山精密"},
  "ok": true,
  "output": "工具的实际输出",
  "message": "Lucas 调用 wiki_recall: 东山精密"
}
```

同一份事件可以同时服务两种界面：`message` 用于聊天区的简短过程摘要，其他字段用于 Trace 面板的详细视图。这样展示方式可以变化，执行协议仍然稳定。

## 2. 为什么把 Trace 存在助手消息上

一次用户提问最终对应一条助手消息，工具调用正是生成这条回答的过程。把 `traceSteps` 和回答一起保存有三个好处：

- 生命周期天然一致，不需要额外维护“run 与 session message 如何关联”的数据库表。
- 现有 session API 已经负责消息持久化，不需要新增存储系统。
- 读取历史会话时一次请求就能恢复回答和 Trace，不会产生额外请求瀑布。

代价是消息 JSON 会变大。当前业务工具本身已经对过大的资料结果做边界截断，所以本阶段保留实际工具输出，不再由 Runner 额外截成 500 字摘要。后续如果 Trace 体积成为真实问题，再考虑把大输出保存为 artifact，并在消息中保存引用。

## 3. 实时状态与历史状态为什么分开

执行期间，Trace 尚未进入最终助手消息，因此前端维护一个临时的 `liveTurn`；收到完成或错误事件后，完整 `traceSteps` 写入助手消息并走原有 session 保存流程。面板渲染时组合“已保存的历史轮次 + 当前 liveTurn”。

这避免了每收到一个流式事件就写一次 session，也避免半完成 Trace 污染持久数据。异常和用户取消同样会生成一条带错误 Trace 的助手消息，因此失败过程也能回看。

## 4. single 模式下只呈现 Lucas 的动作

底层暂时保留 `dispatch`、`researcher_start` 等兼容事件，但 UI 不再暴露“选择研究员”这套旧心智模型。过程摘要统一为：

1. Lucas 收到问题。
2. Lucas 开始分析。
3. Lucas 调用某个工具。
4. Lucas 完成分析或分析失败。

对已经保存的旧消息，展示层会把“已选择研究员：Lucas”等旧文案归一化并去重，不修改历史原始数据。

## 5. 布局取舍

宽屏使用固定 360px 的最右侧栏，聊天与 Wiki 仍各自滚动；较窄屏幕改成覆盖式抽屉，避免三栏同时挤压正文。Trace 统一由顶部最右侧按钮展开或折叠，避免面板内出现重复控制。工具详情默认折叠，只有需要排查时才展开输入输出，减少视觉噪音。

## 验收方式

- 后端契约测试锁定结构化 `tool_step` 字段和完整输出。
- TypeScript 生产构建验证消息类型、组件 props 与布局代码。
- 真实页面验证默认展示、隐藏/恢复、实时轮次、工具详情展开、桌面和窄屏布局，以及浏览器控制台无错误。
