# 对话主界面重设计：用阅读节奏替代卡片堆叠

## 这次解决了什么

原来的对话区把用户问题、分析过程和回答都铺满可用宽度，并为过程信息增加整行边框。屏幕越宽，文字行长越难阅读，重复卡片也会抢走回答正文的注意力。这次保留会话、Wiki 联动和 Trace 数据结构，只调整主对话区的视觉表达，同时删除顶部未形成完整工作流的搜索框。

## 1. 对话界面的核心是阅读列

聊天区域虽然可以很宽，但正文不应该跟随容器无限拉伸。新的消息区使用固定最大阅读宽度并居中展示，使 Trace 打开、关闭或用户拖动栏宽时，回答的行长仍保持稳定。用户问题使用右侧短气泡，助手回答使用无卡片正文，两种角色依靠对齐和留白区分，不依赖大面积背景色。

## 2. 过程信息应该低于答案正文

分析过程对排查和理解 Agent 很重要，但它不是每次阅读的主内容。历史过程改成轻量 disclosure，默认只显示步骤数量；展开后用一条左侧轨道组织步骤。运行中的过程保持可见，Trace 面板继续承载完整工具输入输出。这样聊天区和 Trace 各自承担不同的信息密度。

## 3. 输入器是持续操作的锚点

输入器改为悬浮在内容底部的多行 composer，正文预留足够底部空间，避免最后一条消息被遮挡。textarea 根据内容自动增高，Enter 发送，Shift+Enter 换行。中文输入法组合状态继续通过 `isComposing`、composition ref 和 `keyCode 229` 三层判断保护，确认候选词不会误发送。

## 4. 空状态只提供下一步

空状态不再强调产品口号，而是直接回答用户此刻需要做什么：选择一个研究起点或输入问题。建议入口保留真实 Wiki 数据生成逻辑，宽屏采用三个横向入口，窄屏自动切换为单列，不增加装饰性渐变和自动动画。标题上方的魔法图标只承担视觉引导，因此不使用按钮式描边。

## 5. 为什么不引入新的组件库

项目已经使用 Tailwind v4 和 Lucide。此次目标是修复排版、间距、层级和状态，而不是替换整个设计系统。继续沿用现有依赖能降低改动范围，也避免同一页面混入两套圆角、颜色和交互语言。

## 验收方式

- 生产构建验证 TypeScript、组件 props 和 Tailwind 类名。
- 真实页面分别检查 1440px 宽屏、390px 移动端、亮色和暗色模式。
- 验证顶部搜索完全消失、长回答行长稳定、Trace 开关不改变阅读宽度、多行输入自动增高且发送按钮状态正确。
- 使用全新浏览器页检查框架错误覆盖层和控制台错误。
