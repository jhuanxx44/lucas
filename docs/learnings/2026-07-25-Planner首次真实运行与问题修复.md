# Planner 首次真实运行：4 个发现与修复

## 背景

Lucas 刚刚接入了 `update_plan` 规划工具（Codex 式哑工具方案），完成了前端 PlanCard 可视化和
eval task。我们用真实模型（deepseek-v4-flash）跑了 4 个场景做首次端到端验证。

## 4 个发现

### 1. LLM 的惯性：先动手，后补计划

我们的 prompt 写的是"第一步必须是 tool（wiki_recall 或 web_search）"。对于复杂调研任务，
模型的第一反应是直接搜索，搜完了才想起来「哦，我应该先规划」。这不是模型傻，是我们的规则
自己挡了自己的路——`update_plan` 也是 tool，但我们没说它可以是第一步。

**教训**：给 LLM 写规则时，要考虑规则之间的优先级和例外。不能说"A 必须在 B 之前"又说"C 必须
第一步做"，却不说清楚 C 算不算 A。

### 2. Plan 是愿望清单，不是路线图

模型能产出不错的计划（6 步，层次清晰），但执行时会做大量计划外的事情——多搜 2 次、
多写 2 个文件、先覆盖再修补。Plan 制定出来之后，模型没有把它当约束，而是当成建议。

这暴露了一个更深的问题：哑工具方案中，plan 只是上下文中的一段文字，模型可以选择遵循
也可以选择忽略。要让模型真正遵循计划，要么在 prompt 里反复强调，要么把 plan 做成
runner 级的硬约束（后者在我们当前的 Phase 2 范围内不做）。

**教训**：哑工具的"低实现成本"优势，对应的是"低可靠性"代价。如果后续实验证明 prompt 级
强调仍然不足以让模型遵循计划，就应该考虑 Phase 2 的重 Planner 方案（harness 帮你管步骤）。

### 3. 没有操作顺序的脚手架，模型会"跳跃"

模型在单步 JSON 协议下，每一步只看到当前状态，没有全局执行顺序的概念。它先写了行业报告
再写公司档案，不是因为不会写——是因为它把"先写哪个"当成了自由选择，不知道依赖关系。

加了"先收集再产出、先档案再报告"的规则后，等于给了模型一个执行顺序的脚手架。

**教训**：LLM 在多步骤任务中不会自动推导最优执行顺序，需要显式的顺序约束。Agent Harness 的
价值之一就是把这类"领域执行知识"编码进 prompt 或工具协议。

### 4. 重复成功比重复失败更隐蔽

我们的原有规则覆盖了"不要重复失败的调用"，但没有覆盖"不要重复成功的调用"。模型搜了
中际旭创、拿到了信息、继续做了其他事，然后回来又搜了一次中际旭创——不是上次失败了，
而是忘了自己已经搜过了。

**教训**：24 步以上的长程任务中，模型的"上下文遗忘"是真实问题。随着步数增加，早期的
observation 在 prompt 中的权重降低，模型倾向于重新验证。这正好是 Phase 4（Context 管理）
要解决的问题之一：通过 Context selection 把关键 observation 保留在注意力窗口内。

## 启示

这 4 个修复全部落在 prompt 层。如果下一轮验证后问题仍然存在，说明 prompt 的能力边界
已经到了，需要考虑代码层的机制——比如 runner 强制 plan 步数上限、或给 plan step 加
工具白名单。

真正的分水岭是：**当 prompt 修无可修时，机制实验才真正开始。**
