# 完整产品 Trace 导出

## 机制假设

产品页面右侧需要的是低噪声的执行摘要，而调试和评估需要的是可复盘的完整轨迹。两者共用一份数据会产生冲突：增加模型输入输出后，右侧页面会迅速被大量技术细节淹没。

本次改动验证的假设是：保留现有 `traceSteps` 作为展示投影，另建只持久化和导出的 `runtimeTrace`，可以同时保持 UI 简洁和提高导出覆盖率。

## 固定任务与结果

固定任务使用两步轨迹：模型先调用 `wiki_recall`，再根据 observation 返回最终答案；另用一个带 provider reasoning 的单步回答验证 reasoning 通道。

改动前，导出文件只包含用户问题、展示摘要和工具结果：模型输入与原始输出覆盖率为 0/4，reasoning 覆盖率为 0/1，最终回答也没有进入导出 turn。

改动后，同一任务可以从 schema v2 文件中读到：

- run 配置和 system prompt；
- 每一步实际交给模型的动态 prompt；
- provider 返回给 Lucas 的 reasoning；
- 模型原始 action JSON，包括工具选择和最终 reply；
- 工具名称、参数、状态和 observation；
- 最终 assistant answer、token 数和 finish reason。

模型输入与原始输出覆盖率提升为 4/4，reasoning 覆盖率提升为 1/1。相关后端测试和前端生产构建均通过。

## 关键设计取舍

`AgentRunner` 新增独立的 `on_trace_event` 钩子，而没有把模型输入输出塞进原有 `on_event`。这样产品展示事件协议仍只承担摘要、工具步骤和回答流，已有 UI 和 Eval 调用方不会收到额外事件。

前端把隐藏事件随 assistant message 一起保存，因此刷新页面或切换会话后仍可导出，不依赖服务端临时文件。连续 reasoning delta 会在同一步内合并，保留完整文本但避免一个回答产生数百条碎片事件。

旧会话无法倒推出当时没有采集的模型原始输出。schema v2 会把这类 turn 标为 `legacy_partial`，仍导出已有问题、最终回答和展示步骤；新产生的 turn 标为 `complete`。

“完整”只覆盖 Lucas 实际收到或生成的数据。provider 没有返回的内部状态无法记录，也不会伪造。
