# Lucas 终态愿景：量化策略搭建助手

日期：2026-07-28

## 核心想法

Lucas 的终态不只是做金融建模（已写），还可以成为一个**量化策略搭建平台的"前端"**，面向初学者用户。

### 问题

初学者想验证一个量化策略想法时，面临的不是"策略对不对"，而是一堆工程坑：

- 数据源接入（行情、财务、情绪、另类数据），各家 API 协议不同、付费模型各异
- 回测框架搭建，survivorship bias、look-ahead bias、滑点、手续费建模
- 券商接口对接，实盘和模拟盘的订单路由、持仓同步
- 风控边界：仓位上限、止损、最大回撤、流动性约束
- 结果解读：夏普、最大回撤、胜率这些指标怎么理解，怎么避免过拟合

这些问题对老手是体力活，对新手是劝退墙。新手真正需要的是一句话描述策略 → 看到回测结果 → 觉得靠谱就上模拟盘试跑。

### Lucas 的角色

Lucas 不是平台本身，而是平台的 **Agent 界面层**。平台负责：数据管线、回测引擎、券商网关、风控执行。Lucas 负责：理解用户意图、翻译成平台操作、解释结果、引导迭代。

```text
用户（自然语言）→ Lucas（Agent）→ 量化平台（引擎）
                  ↑ 解释、引导、纠错   ↓
                  ←――――――――――――――――――
```

### 与现有路线的关系

- 现有的 `daily_stock_analysis` 数据源清单已经是前置调研。
- Agent Harness 的 Planning、Tool、Validation 等机制实验，正好为这种"理解意图 → 调用工具 → 解释结果"的交互模式打基础。
- 不需要现在就铺平台能力；先在 Harness 实验中验证"Agent 能正确翻译策略意图并调用回测/数据工具"这条链路。

## 开闭源与仓库边界

长期采用“开源 Agent + 闭源量化平台”的划分：Lucas Agent 负责理解、规划、调用工具和解释结果；量化平台负责数据、回测、风控、账户与可信执行。两者通过公开、版本化的 API/SDK 连接。

```text
┌─────────────────────────────────────┐
│ lucas-agent（开源）                 │
│                                     │
│ Harness / Planning / Tool / Trace   │
│ Agent UI                            │
│ 通用 prompts                        │
│ 策略 DSL / Schema                   │
│ Quant Platform SDK                  │
│ 本地 Mock / 教学型回测实现          │
│ 公共回归测试                        │
└────────────────┬────────────────────┘
                 │ Versioned API
                 ▼
┌─────────────────────────────────────┐
│ lucas-quant-platform（闭源）        │
│                                     │
│ 数据管线与标准化                    │
│ 生产级回测引擎                      │
│ 风控与组合管理                      │
│ 模拟盘 / 实盘执行                   │
│ 任务调度、审计、监控、计费          │
│ 私有数据、参数、评测与运行记录      │
└─────────────────────────────────────┘
```

### 仓库规划

Agent 与平台使用两个相互独立的仓库，而不是依靠父子目录表达产品归属：

```text
lucas-agent/             # 公共仓库，可独立安装、运行、测试和发布
lucas-quant-platform/    # 私有仓库，提供量化平台服务
```

依赖方向固定为 `lucas-agent → 公开 API/SDK → lucas-quant-platform`。开源 Agent 不读取平台仓库文件，也不 import 私有模块。本地联调通过平台地址配置连接；未来如需一体化开发环境，可由私有集成配置、Docker Compose 或 Git submodule 固定两边版本，但不改变两个仓库的独立性。

### 边界原则

- Agent 侧公开 Harness、通用工具、Trace、Eval Harness、产品 UI、策略 schema、平台客户端和可独立运行的 Mock 实现。
- 平台侧保留数据清洗与版本、生产级回测语义、滑点和成交模型、组合风控、账户状态、券商网关、审计监控、计费以及私有评测。
- Agent 只表达策略和操作意图；仓位、杠杆、可交易标的、人工审批、幂等下单和 Kill Switch 等安全规则必须由平台确定性执行，不能依赖 prompt。
- 即使用户修改开源 Agent，也不能绕过平台的权限与风控边界。
- 当前 Lucas 项目自然演进为未来的 `lucas-agent`；在平台建设条件成熟前，不提前搭建完整量化平台。

## 同类产品调研：Agent 数据能力开放模式

### 已观察到的产品形态

市场上已经出现“闭源量化平台 + 可安装 Agent Skill”的实现。其公开 Skill 当前主要开放数据访问，不开放回测和交易执行：

- 下载日线、分钟线、Tick 等历史行情，支持单标的和批量下载。
- 查询历史或实时 K 线及部分扩展行情字段。
- 获取股票列表、指数或自定义板块成分。
- 查询股票、期货等合约的名称、上市日、涨跌停、股本、保证金率、合约乘数和交易状态。
- 下载并查询资产负债表、利润表、现金流量表、股本、股东数和主要股东等财务数据。
- 查询内外盘、委买委卖量及历史涨跌停价格。

其 Skill 包明确不包含策略回测、参数优化、模拟交易、实盘下单、撤单、持仓管理、账户查询或风控执行。“自然语言生成策略”即使存在，也属于平台的另一条产品链路，不等于数据 Skill 本身具备完整策略闭环。

### 技术模式

该实现本质上是“API 知识包 + 本地辅助脚本”，不是独立的 MCP 或结构化 Tool Server：

```text
SKILL.md API 说明
    ↓
Agent 生成或选择 Python 调用
    ↓
AI 客户端执行本地脚本
    ↓
厂商 SDK
    ↓
闭源数据平台与本地缓存
```

安装入口本身也是一个 Skill，负责检测终端和 Python 环境、逐项取得用户确认、安装 SDK、把多个数据 Skill 复制到不同 AI 客户端的全局目录，并验证依赖是否可导入。

这种方式接入快，但 Skill 同时承担了 API 文档、示例、安装流程和部分执行指导。参数校验、权限、超时、结果 schema 与错误语义没有统一运行时保证；安装到全局目录后也可能影响无关项目的 Context。

### 供应链观察

调研时发现，安装文档声明的压缩包校验值与下载节点实际返回文件不一致，关联的能力目录页面也不可访问。按照该产品自己的安装规则，此时应拒绝安装。其安装包还使用明文 HTTP 下载和 MD5 校验，保护强度有限。

这说明 Lucas 将来发布 Skill 或平台 SDK 时至少需要：

- 使用 HTTPS 和现代摘要算法，发布不可变版本及校验值。
- 签名 manifest 或发布包，并让安装器在执行前验证来源、版本和内容。
- 下载、安装、覆盖和全局配置分别取得用户授权。
- 默认项目级、按需加载，避免把领域指令永久注入所有会话。
- 安装包校验失败时停止，不以自动重试或忽略校验继续执行。

### 对 Lucas 边界的启示

该产品形态验证了“开放 Agent/Skill，闭源数据与交易平台”在工程上可行。Lucas 可以沿用这个大边界，但把 Skill 与 Tool 的职责分开：

```text
Skill：何时调用、业务语义、如何解释结果
Tool：参数 schema、权限、超时、执行和结构化结果
Platform：数据质量、回测、账户、风控和可信执行
```

Lucas 不应把“一句话生成简单策略”本身视为差异化。更值得验证的方向是多后端适配、结构化策略规格、可重复实验、Trace 与证据、防未来函数和数据泄露校验、教学式解释，以及模拟盘到实盘之间的平台侧安全审批。

第一阶段无需自建完整行情、回测和券商基础设施。可以先让 Lucas 成为现有数据与回测后端之上的开放 Agent 和统一控制层；只有真实任务证明第三方能力成为限制时，再逐步把相应模块纳入闭源平台。

## 待后续细化

- 平台后端选型（自建 vs 集成现有开源回测框架）
- 数据源优先级和接入顺序
- 策略 DSL 还是自然语言全程
- 模拟盘 → 实盘的过渡机制
- 面向初学者的教学式交互设计
