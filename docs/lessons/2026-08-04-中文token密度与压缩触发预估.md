# 中文 token 密度实测 0.60，压缩触发预估会系统性偏晚

## 问题

`harness/runner.py` 的 `DEFAULT_TOKENS_PER_CHAR = 0.35`，注释写「无校准数据时的默认
token/字符 系数（保守偏高）」。对中文散文实际是**偏低**约 71%。

后果：压缩触发线基于该系数预估，实际 token 数比预估高，因此**压缩会比预期更晚触发**；
在没有校准数据的第一次预估上尤其明显。

## 实测数据

CTX-01 长任务 baseline run（deepseek-v4-flash），每篇备忘录 5,293 字符，从相邻步的
`prompt_tokens` 增量反推：

| 增量 | tok/char |
|---|---:|
| 10,673 − 7,306 = 3,367 | 0.636 |
| 14,062 − 10,929 = 3,133 | 0.592 |
| 17,446 − 14,319 = 3,127 | 0.591 |
| 44,915 − 41,722 = 3,193 | 0.603 |

稳定在 **0.59–0.64**。

与既有记录一致：`docs/experiments/2026-07-27-chunk大小对照实验.md` 记录过「中文 token 密度
差异可达 2 倍以上」，化学式、数字、代码块会显著抬高密度（该实验中 `六氟磷酸锂.md` 达约
2.3 token/字符）。0.35 只适用于密度很低的文本。

## 正确做法

- **按字符数估算 token 预算时留足余量**，或用真实 tokenizer 计数。做实验设计（如按窗口倍率
  反推 fixture 篇幅）时，用 0.6 而非 0.35 估中文散文。
- **不要凭该常量判断压缩会在第几步触发**。runner 有 `_calibrated_ratio` 动态校准
  （`CALIBRATION_WINDOW = 3`），真实运行几轮后会自我修正；受影响的主要是首次预估。
- **不要顺手改这个默认值**。它会改变所有任务的首次触发时机，属独立变更，须走单变量对照
  （若要改，需覆盖中英混排、含代码块、纯数字表格等不同密度的任务）。
- 想确认真实峰值就跑一次 `LUCAS_CONTEXT_WINDOW=0` 探针，从 trace 的 `model_call_finished`
  读 `prompt_tokens`，别用系数推。
