# 前端输入法（IME）回车陷阱：组合回车被当成提交

## 问题

中文输入法下，用户在输入框按回车有两种意图：

- 提交输入法组合：把拼音/候选确认进输入框；
- 提交业务动作：发送消息、确认重命名、新建目录等。

如果回车处理不区分这两种意图，用户按回车"确认组合"时消息会被直接误发。

## 为什么容易写错

浏览器对"组合结束"和"回车 keydown"的派发顺序不统一：

- Chrome 系：`keydown(Enter, isComposing=true)` 先到，之后才 `compositionend`；
- Firefox/Safari 及部分输入法：`compositionend` 先到，提交组合的回车 `keydown` 后到，且可能跨事件循环任务派发。

早期修复用 `onCompositionEnd` + `setTimeout(0)` 复位组合标志，隐含假设"compositionend 与 keydown 在同一任务内到达"。跨任务派发时 `setTimeout(0)` 先执行、标志已复位，回车被当成普通发送——bug 回归。这就是"上次修好了，换个浏览器/输入法又出现"的原因。

## 正确的守卫模式

参考实现：`web/src/components/ChatInput.tsx`。

组合开始置位标志；组合结束时记录时间戳；回车 `keydown` 满足以下任一条件即不提交：

- `isComposingRef.current`：组合进行中；
- `e.nativeEvent.isComposing` / `keyCode === 229`：浏览器原生的组合标记；
- `Date.now() - compositionEndRef.current < 300`：组合结束后的短窗口，覆盖"compositionend 先到、keydown 跨任务后到"的顺序。

关键点：**不依赖事件顺序**，用"组合结束时间戳 + 短窗口"兜底，而不是定时器复位标志。

## 适用边界

任何输入框/文本域的回车提交逻辑（发送消息、重命名、新建目录等）都套用这个模式；不要写"裸 `e.key === "Enter"` 即提交"。

## 验证方法

在真实页面用 CDP/Playwright 模拟组合事件序列（`compositionstart` → `compositionend` → `keydown Enter`），验证四种场景：

1. 组合进行中回车 → 不提交；
2. 组合结束、短窗口内回车（跨任务到达）→ 不提交；
3. 无组合的普通回车 → 正常提交；
4. 组合结束超过窗口期后的回车 → 正常提交。
