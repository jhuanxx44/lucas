# Wiki 规模化构建与检索实验计划

日期：2026-07-27  
状态：已完成

## 1. 目标

构建一个来源真实、内容可追溯、结构接近 Lucas 生产 Wiki 的中高质量冻结母库，
然后控制每个 task/trial 中 Agent 实际可见的知识库大小，回答三个问题：

1. TF-IDF 和 BM25 的排序质量是否随知识库规模发生稳定变化？
2. 知识库增大是否影响 Agent 的最终任务成功率、稳定性、成本和延迟？
3. 离线检索指标的变化是否真的会传导到 Agent 最终 outcome？

本计划不预设 TF-IDF 或 BM25 胜出。生产召回是否切换，只根据端到端实验结果决定。

## 2. 必要假设与边界

- 第一版母库目标为约 500 篇唯一文档；规模档位暂定 50、100、200、500。
- 500 篇用于覆盖“小型到中型”范围，不能据此外推到数千或百万文档。
- 语料尽量通过爬虫从真实网页获取，不复制文档、不用模板或 LLM 凭空生成内容凑数。
- LLM 只负责分类、去噪、归并、摘要和结构化，不允许补充来源中不存在的事实。
- 抓取快照和整理产物都是评估派生数据，不写入项目 `raw/`。
- 先完成离线检索矩阵，再选择有区分度的条件运行成本更高的 Agent 端到端实验。
- 当前 50 篇最小规模是暂定值。如果单个 task 所需 ground truth 超过可容纳范围，
  应提高该 task 的最小规模，不能为了维持数字而移除必要证据。

## 3. 两条实验轨道

### 3.1 受控干扰轨道（主要因果实验）

对每个 task 和 subset seed：

- 最小子库包含该 task 的全部 ground truth；
- 后续规模只加入非相关或弱相关干扰文档；
- 同一 seed 的 50 ⊂ 100 ⊂ 200 ⊂ 500；
- 每个规模保持相近的领域、来源等级和文档长度分布；
- 使用至少 5 组 seed，防止某一组干扰文档偶然偏向某个算法。

该轨道只操纵干扰文档数量，用来判断“规模本身是否改变检索难度”。

### 3.2 自然增长轨道（产品模拟实验）

按冻结的抓取/入库顺序构造嵌套子库，相关文档也可能随着规模增加。它模拟真实产品中
“知识越来越多，可回答问题也越来越多”的过程，但不能用于单独归因排序算法差异。

两条轨道分别报告，不合并成一个结论。

## 4. 母库目录与不可变数据协议

建议目录：

```text
evals/corpora/wiki-scale-v1/
├── sources/
│   ├── catalog.jsonl             # 来源、抓取时间、状态、hash、许可信息
│   └── snapshots/                # 抓取后的原始 HTML/Markdown 快照
├── master/
│   └── wiki/                     # LLM 整理并通过质量门禁的 500 篇冻结母库
├── quality/
│   ├── validation.json           # 确定性校验结果
│   ├── review-sample.jsonl       # 人工/LLM 抽检记录
│   └── duplicates.json           # 精确和近重复报告
├── queries/
│   ├── dev.json
│   └── test.json
├── manifests/
│   ├── controlled/<task>/<seed>/n0050.json
│   └── natural/<seed>/n0050.json
└── VERSION.json                  # 构建配置、工具版本、整体 hash
```

约束：

- `sources/snapshots/` 在版本冻结后视为不可变；更新来源时发布 `wiki-scale-v2`。
- `master/wiki/` 只能由构建流水线生成，不允许 Agent trial 回写。
- trial workspace 根据 manifest 复制可见页面并重新生成 `wiki/index.md`。
- manifest 之外的文件、标题和路径不得通过索引、缓存或日志泄漏给 Agent。
- 禁止使用 symlink；Eval Harness 继续复制到独立临时 workspace。

## 5. 中高质量 Wiki 的构建方案

### 5.1 内容结构

第一版建议约 500 篇，按检索难度而非简单行业数量分层：

| 类型 | 目标数量 | 用途 |
|---|---:|---|
| 半导体、光通信等目标领域 | 150 | 主要相关文档和跨文档综合 |
| AI、云计算、通信设备、汽车电子等近邻领域 | 200 | 高难度语义干扰 |
| 消费、餐饮、文化、体育等远端领域 | 150 | 一般噪声和跨域查询 |

同时控制公司、技术概念、行业、产品和事件等页面类型，避免所有文档都是公司百科。

### 5.2 来源优先级

按以下顺序选源：

1. **一级来源**：公司官网/投资者关系、监管披露、政府和标准组织、论文或技术规范。
2. **二级来源**：中文维基百科等可核验百科、权威行业协会、可信研究机构。
3. **补充来源**：高质量主流媒体或专业技术媒体，只用于一级来源缺失的背景和事件。

避免：

- SEO 内容农场、无署名转载、问答聚合、搜索结果摘要；
- 无稳定 URL、无法重复抓取或正文主要依赖登录的页面；
- 版权或 robots 规则明确禁止抓取的站点；
- 单一来源覆盖全部领域，导致写作风格和词汇分布过于一致。

每篇 Wiki 原则上至少有一个可访问来源；涉及关键数字、时间变化或争议判断时，优先使用
两个独立来源或一个权威一级来源。

### 5.3 抓取清单先行

先维护 `source-plan.jsonl`，再执行抓取。每条候选来源至少包含：

```json
{
  "doc_id": "company-tsmc",
  "target_path": "companies/半导体/台积电.md",
  "domain": "半导体",
  "page_type": "company",
  "source_tier": 1,
  "urls": ["https://example.com/source"],
  "reason": "覆盖晶圆代工、工艺节点和竞争定位"
}
```

抓取完成后在 catalog 中追加：canonical URL、HTTP 状态、抓取时间、页面标题、发布者、
语言、正文字符数、内容 SHA-256、抓取工具和版本、许可/robots 备注。

抓取失败、正文过短或疑似登录页只记录状态，不交给 LLM 猜测补全。

### 5.4 抓取实现

基于现有 `scripts/build_wiki_fixture.py` 拆成可恢复的两阶段流水线：

1. `crawl_wiki_sources.py`：只负责抓取和保存快照，支持断点续跑、超时、有限重试、
   速率限制、HTTP 状态和 hash 记录。
2. `compile_wiki_corpus.py`：读取冻结快照，调用 LLM 整理，执行 schema/引用/重复校验，
   通过后写入 `master/wiki/`。

不让抓取脚本直接覆盖已通过审核的母库。抓取和整理失败都应留下明确状态，不能静默跳过。

### 5.5 LLM 整理规则

LLM 的输入只能是当前文档对应的来源快照和明确的页面 schema。未来新增的整理 prompt
放在 `prompts/evals/wiki-corpus-compile.md`，并标注实际使用的 `llm-weight: heavy`。

输出规则：

- 只保留来源能直接支持的事实，不调用模型自身知识补全；
- 多来源内容按主题归并，冲突信息并列说明来源和时间，不自行裁决；
- 保留实体名、缩写、产品名、关键时间和关键数字，避免摘要丢掉可检索词；
- 删除网站导航、广告、重复段落、参考文献列表噪声；
- 不为了统一篇幅扩写短文，也不为了流畅删除关键限定条件；
- summary 为 2–4 句中文 TL;DR，必须能从正文和来源推出；
- 数字、日期、市场份额、性能指标和关键判断必须带来源标记，例如 `[S1]`；
- 文末保存来源映射，保证 `[S1]` 能回溯到快照和 URL；
- 无法可靠整理时输出失败状态，不生成页面。

建议页面格式：

```markdown
---
title: 台积电
type: company
industry: 半导体
as_of: 2026-07-27
summary: "..."
source_ids: [S1, S2]
---

# 台积电

正文事实……[S1]

## 来源

- [S1] 来源标题 — URL（抓取日期）
```

### 5.6 质量门禁

确定性门禁全部通过后，页面才能进入母库：

- frontmatter schema、`summary`、`source_ids` 100% 合法；
- 页面中的来源标记都能解析到 catalog 和本地快照；
- 所有数字、日期和百分比附近必须存在来源标记；
- 空正文、抓取错误页、登录页、乱码页为 0；
- 精确重复为 0，近重复率不超过 2%；
- `index.md` 与实际页面完全一致；
- 页面路径、类型和领域与 source plan 一致；
- 母库构建两次的文件 hash 一致，保证确定性。

主观质量只用于确定性规则覆盖不到的部分：从每个领域和来源等级分层抽检至少 10%，
总数不少于 50 篇。检查事实是否被来源支持、是否遗漏关键限定、摘要是否准确、是否存在
LLM 自行补写。LLM reviewer 允许返回“不确定”，不确定和高风险页面进入人工复核。

建议首版验收线：

| 指标 | 门槛 |
|---|---:|
| 有效来源和可回溯快照 | 100% |
| 一级/二级来源占比 | ≥80% |
| schema 与引用校验 | 100% |
| 精确重复 | 0 |
| 近重复 | ≤2% |
| 抽检事实支持率 | ≥95% |
| 抽检中无来源的关键数字 | 0 |

任何门禁未通过时先修复语料，不进入检索实验。

## 6. 查询集和 Ground Truth

旧查询只有 15 条，不足以支持规模结论。新母库冻结后构建至少 60 条、目标 100 条查询，
覆盖：公司事实、概念解释、跨文档综合、近邻干扰、长尾实体、缩写/同义词、证据不足和
不存在判断。

Ground truth 基于完整母库标注：

1. TF-IDF 和 BM25 各取 Top-20 合并成候选池；
2. 加入随机文档和同领域文档检查漏标；
3. 对候选文档标注 0–3 级相关性；
4. 开放式综合题人工复核，允许多个相关文档集合；
5. 按查询而不是按文档拆分 dev/test；参数只在 dev 调整，test 只用于最终报告。

不能沿用扩库前的 ground truth：新文档可能是真实相关文档，漏标会把正确召回判成错误。

## 7. 可见子库物化

manifest 至少记录：corpus version、track、task/query id、seed、size、文档路径列表和整体 hash。

每个 trial 开始前：

1. 从冻结 `master/wiki/` 复制 manifest 指定页面到临时 fixture/workspace；
2. 只根据可见页面重新生成 `wiki/index.md`；
3. 校验页面数、路径集合和 manifest hash；
4. 扫描 workspace，确认不存在 manifest 外页面或指向母库的 symlink；
5. 将 manifest id/hash 写入 run manifest 和 trace；
6. trial 结束后按现有 Evaluation Harness 规则归档并清理 workspace。

优先在 RETRIEVAL-SCALE 专用 runner 中完成物化，不把 Wiki 业务概念写进通用 Agent Harness。
只有多个评估任务都需要 manifest fixture 时，才提取为 Evaluation Harness 的通用能力。

## 8. 实验矩阵

### 8.1 离线检索实验

完整矩阵：

- retriever：TF-IDF、BM25；
- size：50、100、200、500；
- subset seed：至少 5；
- query：test 集全部查询；
- representation：同一 tokenizer、同一查询 token、同一正分过滤规则。

指标：Recall@5/10、MRR、NDCG@5/10、无结果率、检索延迟和构建成本。统计以 query
为主要配对单位，并对 subset seed 聚类；不把同一查询的多次 seed 当成独立查询。

另跑一组“可部署候选”对照：当前生产子串 BM25 vs 具备同一工具接口的 TF-IDF 候选。
这组用于产品决策，可以包含必要的表示差异，但必须与纯打分公式实验分开报告。

### 8.2 Agent 端到端实验

离线实验完成后，选择 3 个规模（建议 50、200、500）和能暴露差异的固定 task，运行：

- 相同模型、temperature、prompt、工具、timeout 和 cost budget；
- 每个 retriever × size × task 至少 3 trials；
- Agent 只能看到当前 manifest 物化出的 Wiki；
- grader 以最终答案事实、证据覆盖和必要文件状态为主，不强制固定工具路径。

主要指标：最终成功率、事实覆盖率、无依据结论率。辅助指标：检索调用数、steps、tokens、
成本、延迟、失败方差。trace 用于解释检索排名如何传导到最终答案。

如果完整矩阵成本过高，先用离线结果筛选规模和 task，不减少每个保留条件的重复 trials。

## 10. 决策规则

- 如果离线指标有差异但 Agent outcome 无稳定差异，不切换生产实现。
- 如果候选只在 dev 胜出、test 不胜出，视为调参过拟合。
- 如果大库下质量提高但延迟/成本超过预算，同时报告收益和代价，不只报准确率。
- 如果不同 seed 结论方向不一致，继续扩大查询和干扰样本，不下算法结论。
- 只有 test 集和 Agent outcome 都稳定改善，且可靠性/成本可接受，才切换生产检索器。

## 11. 明确不做

- 不复制、轻微改写同一文档来凑 500 篇。
- 不让 LLM 脱离抓取来源写百科内容。
- 不用旧 15 条查询直接为 500 篇母库下最终结论。
- 不让小规模子库的 index 或缓存泄漏完整母库信息。
- 不在本阶段建设通用向量数据库、完整数据平台或分布式爬虫。
- 不把评估物化逻辑写进生产 Agent Harness。

## 12. 交付物

- 冻结母库和可追溯来源 catalog；
- 抓取、整理、校验、manifest 生成和物化脚本；
- 60–100 条 dev/test 查询及 ground truth；
- 离线检索实验结果和 Agent 多 trial 结果；
- 完整实验报告、运行日志和中高质量知识库构建教程。
