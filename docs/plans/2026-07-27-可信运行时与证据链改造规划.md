# 可信运行时与证据链改造规划

日期：2026-07-27  
状态：规划中  
适用范围：Lucas Agent Harness、产品运行 trace、Evaluation Harness

## 1. 改造目标

把 Lucas 从“模型能完成一轮任务并生成回答”改造成“系统能够证明任务实际完成，并说明回答依据”的 Agent Harness。

最终由运行时和环境状态判定任务结果，模型输出只作为候选动作或候选答案。工具返回、文件产物、计划状态、错误和终止原因必须可追踪、可验证、可复盘。

本规划不以增加更多 prompt 规则为主要手段，也不提前建设 Memory、向量数据库、多 Agent 或通用事实核验模型。

## 2. 当前现状

### 2.1 已有能力

- `harness/runner.py` 已有单 Agent JSON action 循环，支持工具调用、答案输出、步数、超时、预算和重复结果检测。
- `harness/trace.py` 已有 append-only JSONL 记录器；Runner 已记录 `model_call`、`tool_call`、`step`、错误和 artifact 引用等事件。
- `harness/tools/base.py` 已有 `ToolResult`，能表达 `ok`、`invalid_input`、`denied`、`timeout`、`error`。
- `evals/` 已有隔离运行、trace 完整性检查和结果 grader 的基础设施。
- wiki 文件写入和索引更新已经能够在实际运行中落盘。

### 2.2 这次 trace 暴露的问题

2026-07-27 的半导体设备调研 trace 显示：

1. 最终答案包含大量精确数字，但没有逐条证据引用，来源主要是二手行业文章。
2. system prompt 要求先 `wiki_recall` 再联网，但实际先执行了 `web_search`，之后才召回 wiki。
3. 模型通过 `update_plan` 自行把步骤标为 completed，运行时没有根据真实工具结果校验。
4. 产品导出的 trace 只保留模型输入、模型输出和 reasoning，工具调用和工具返回没有作为独立事件出现；工具结果只能从下一轮上下文反推。
5. 配置中的 `max_steps: 0`、`timeout_seconds: 0` 代表不限制，缺少安全默认上限。
6. 模型输出 `answer` 后，Runner 直接将其视为 `completed`，没有候选答案验证阶段。

### 2.3 共同根因

上述问题不是若干独立的 prompt 缺陷，而是同一个边界问题：**模型生成的叙述同时承担了决策、事实、执行状态和完成声明四种职责。**

当前链路近似为：

```text
模型决定动作 → 工具结果被格式化为文本 → 模型宣布完成 → 系统保存模型叙述
```

可信链路应改为：

```text
模型提出候选动作
  → 运行时执行并记录原始结果
  → 运行时更新事实状态、计划状态和产物状态
  → 模型基于结构化状态生成候选答案
  → 运行时验证候选答案
  → 由环境 outcome 判定成功或失败
```

## 3. 目标架构

### 3.1 三层职责

```text
事实层：工具原始返回、来源、时间、文件 hash、错误
执行层：RunState、计划、预算、权限、重试、终止语义
表达层：模型的 action、summary 和最终 reply
```

- 事实层只能由工具和文件系统产生。
- 执行层只能由 Runner/Runtime 更新。
- 表达层可以被模型生成，但不能反向修改事实层和执行层。

### 3.2 核心状态

新增或完善运行时状态对象：

```python
@dataclass
class RunState:
    run_id: str
    status: str
    step_index: int
    plan: PlanState
    evidence: list[Evidence]
    artifacts: list[ArtifactRef]
    tool_calls: list[ToolCall]
    finish_reason: str | None
```

`RunState` 是运行时真相；trace 是它的不可变审计记录；`AgentResult` 只表示模型交出的候选结果。

## 4. 分阶段改造方案

### Slice 1：可信 trace 和 artifact 记录

目标：先让每次执行都可还原，不改变模型决策策略。

工作内容：

- 为模型调用、工具调用、工具返回、产物创建、步骤结束和 run 结束统一分配稳定 ID。
- 产品 trace 导出完整保留 Runner 已记录的 `tool_call_started`、`tool_call_finished`、`tool_call_error` 等事件。
- 工具原始输出写入 artifact；主 trace 保存 hash、路径、长度、截断状态和有限 preview。
- `run_finished` 必须在成功、错误、超时、取消和预算耗尽时都产生。
- trace schema 增加版本号，并保证 artifact 先落盘、事件后引用。

验收：仅凭 trace 能回答每一步调用了什么工具、是否成功、返回了什么、产生了哪些文件和最终为何停止。

### Slice 2：RunState 和计划状态机

目标：执行状态不再由模型自报。

工作内容：

- Runner 创建并维护 `RunState`。
- `update_plan` 从哑工具改为状态更新 API；至少校验唯一 `in_progress`、合法状态转换和步骤 ID。
- 计划步骤只有在对应动作真实成功后才能进入 `completed`。
- 工具调用状态、重试次数、停滞次数和错误分类进入 RunState。
- 将 `max_steps <= 0`、`timeout <= 0` 改为显式配置语义；产品默认值必须为有限安全值。

验收：模型提交“已完成”但工具没有成功时，运行时状态仍为未完成；超时和步数耗尽能明确区分。

### Slice 3：结构化证据和候选答案验证

目标：最终答案只能引用本轮真实获得的证据和产物。

工作内容：

- 扩展 `ToolResult`，增加 `evidence`、`artifacts` 和 `mutations`。
- `web_search` 为每条结果分配 `evidence_id`、来源 URL、抓取时间和内容 hash。
- 文件工具返回实际路径、写入类型和 SHA-256。
- 最终 action 增加：

```json
{
  "action": "answer",
  "reply": "...",
  "evidence_refs": ["ev-7"],
  "artifact_refs": ["artifact-3"],
  "completed_step_ids": ["search", "write"]
}
```

- Runner 将 `answer` 视为候选终止动作，先做确定性验证；失败时回注结构化错误并允许有限 revision。
- 第一版只校验引用存在、产物存在、完成步骤真实完成，不做全面的中文事实抽取。

验收：没有证据引用的研究答案不能直接通过；声称“已写入”但找不到对应 artifact 时必须失败或要求修正。

### Slice 4：Outcome-first evaluation

目标：以环境最终状态而不是文本观感作为主要验收。

为固定任务增加确定性 grader：

- 目标文件是否存在、路径是否正确、frontmatter/schema 是否有效。
- `raw/` 是否未被修改。
- `wiki/index.md` 是否包含正确链接。
- 关键证据是否来自本轮工具结果。
- trace 生命周期是否完整、是否存在未结束的 tool call。
- 是否出现无证据的完成声明。

每个 trial 分开记录：

```text
AgentResult：模型交出的答案
RunOutcome：文件、证据和环境实际状态
GraderResult：是否达到任务要求
```

验收：同一任务运行多次时，可以比较成功率、无依据作答率、重复调用率、步骤数、延迟和成本。

## 5. 并行主线与兼容策略

这项改造可以和 Wiki 检索实验、语料构建、业务工具、前端展示及独立 grader 并行进行，但共享运行时接口必须集中演进。并行工作的边界如下：

| 工作 | 是否可并行 | 约束 |
|---|---|---|
| Wiki/BM25/TF-IDF 检索实验 | 可以 | 不修改 Runner 的终止语义；通过现有 ToolResult/observation 读取结果 |
| 语料构建和固定 task | 可以 | 只写 `evals/`、派生语料和结果目录，不修改 `raw/` |
| 新业务工具 | 可以 | 遵守兼容的 ToolSpec/ToolResult 接口，并补工具级测试 |
| Slice 1 trace | 可以优先并行 | 事件新增应保持旧导出字段可读 |
| Slice 2 RunState | 需集中实施 | 会改变 plan 和 finish reason 的权威来源 |
| Slice 3 证据与答案协议 | 需接口冻结后实施 | 会改变 ToolResult 和最终 action schema |

### 5.1 向后兼容原则

Slice 3 扩展 `ToolResult` 时，新增字段必须有默认空值，旧工具和旧测试只使用 `status`、`observation` 也应继续工作：

```python
@dataclass
class ToolResult:
    status: str
    observation: str = ""
    evidence: list[Evidence] = field(default_factory=list)
    artifacts: list[ArtifactRef] = field(default_factory=list)
```

兼容要求：

- 旧工具可以暂时只返回 observation，不因为没有 evidence 而导致工具执行失败。
- 新 Runner 能读取旧 ToolResult；旧 trace reader 能忽略新增字段。
- 新字段只在需要证据的任务中强制校验，不改变简单任务的最小闭环。
- 最终答案协议新增 `evidence_refs`、`artifact_refs` 和 `completed_step_ids` 时，先支持旧答案解析，再逐步对研究类任务启用强校验。
- trace schema 升级必须有版本号和迁移/降级读取策略，不能让已有 trace 无法打开。

### 5.2 合并和冻结规则

- Slice 1 可以先合并，为所有并行任务提供统一 trace。
- Slice 2、Slice 3 修改共享核心时，每个 Slice 单独提交并设置接口冻结点；其他分支在冻结点后 rebase。
- 检索实验可以先完成 grader 和 baseline，但不要假设未来的证据字段已经存在；接线在 Slice 3 完成后补一层适配。
- 不同主线不得各自修改 `Runner` 的终止语义、`ToolResult` 字段含义或 trace 事件名称。

## 6. 最终验收目标

### 5.1 运行时语义

- 模型不能直接改变 plan、artifact、tool status 或 finish reason。
- 每次工具调用都有 started 和 finished/error 事件。
- 所有终止路径都有结构化 `finish_reason`：`completed`、`max_steps`、`timeout`、`budget_exceeded`、`error`、`cancelled`。
- 步数、超时和预算都有有限默认值。

### 5.2 证据和产物

- 最终答案引用的 evidence/artifact 全部存在于本次 run。
- 文件操作可以由路径和 hash 证明，而不是依赖模型描述。
- 原始输入目录保持不可变。

### 5.3 Trace 和评测

- trace schema 有版本号，可完整还原 model/tool/observation/artifact/finish 生命周期。
- trace 与结果、grader 分离保存，不能用模型答案替代环境 outcome。
- 固定 smoke 任务和 regression 任务均能自动判定成功或失败。
- 这次半导体设备调研重新运行后，能清楚指出每个数字的来源、哪些结论未核验、wiki 是否真实写入。

## 7. 明确不做的事情

在上述目标完成前，不做以下扩展：

- 不通过继续堆叠 system prompt 来解决执行一致性。
- 不引入自动事实核验 LLM 作为第一道防线。
- 不建设新的 Memory、向量数据库或多 Agent 编排。
- 不把 Evaluation 逻辑硬编码进业务 Agent。
- 不为了 trace 可视化而牺牲原始事件的完整性。

## 8. 推荐实施顺序

```text
可信 trace
  → RunState 与计划状态机
  → 结构化 evidence/artifact
  → 候选答案验证
  → outcome grader 与回归套件
```

每个 Slice 单独提交、单独测试、单独记录实验结果。只有上一 Slice 的验收通过，才进入下一 Slice；不要把 Planner、Validator、Context 等机制实验与可信基线改造混在同一个变更中。
