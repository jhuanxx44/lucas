# Wiki 多证据召回与两阶段精排实验设计

日期：2026-07-27  
状态：待执行

## 1. 背景与实验问题

上一轮 500 页 Wiki 规模实验得到三个关键观察：

1. 在共享 jieba 表示的纯公式对照中，TF-IDF 在 100–500 页的离线 Recall@5 稳定高于 BM25。
2. 机械地把生产子串 BM25 换成子串 TF-IDF 反而明显变差，说明公式优势不能直接转化为工具优势。
3. Agent 的主要失败集中在跨文档任务：只召回一份必要证据、重试后仍缺另一页，或答案正确但引用错误路径。500 页时两种候选工具的 Agent 成功率都降至 0.333。

因此下一轮不再回答“TF-IDF 和 BM25 谁更好”这个过宽的问题，而是回答：

> 在知识库变大时，查询拆分和两阶段精排能否提高多证据覆盖，并稳定传导为 Agent outcome？

## 2. 机制假设

### H1：查询拆分改善多证据覆盖

跨文档问题通常包含多个实体或子事实。将问题拆成 2–3 个互补子查询，分别召回再合并，应该提高“全部必要证据均被召回”的概率。

预期首先改善：

- Complete Evidence Recall@K；
- 最弱证据排名；
- Agent 事实与证据覆盖率；
- 跨文档任务成功率。

### H2：候选池后精排改善前排质量

生产子串 BM25 适合无索引扫描和写后立即可见，但前排排序未必最优。先用子串 BM25 获取高召回候选池，再以共享 jieba TF-IDF 精排，可能同时保留生产召回特性和 TF-IDF 的离线排序优势。

预期首先改善：

- NDCG@5/10；
- 证据进入最终返回窗口的比例；
- Agent 第一次检索后的直接作答率。

### H3：查询拆分与精排存在交互

精排只有在候选池已经包含全部必要证据时才可能生效。预计查询拆分主要改善候选覆盖，精排主要改善候选顺序；两者组合可能优于任一单独机制。

### 零假设

在相同知识库、查询、候选预算和最终返回预算下，查询拆分、精排及其组合不会稳定改善 test 集或 Agent outcome；观察到的差异来自任务、seed 或模型波动。

## 3. 实验边界与必要假设

- 复用冻结母库 `wiki-scale-v1`，不重新抓取或修改 500 页 Wiki。
- 复用 50/200/500 页 controlled manifest；100 页只用于离线趋势，不进入首轮 Agent 实验。
- 主要研究 2–3 份必要证据的跨文档任务，不把单页事实题的高成功率稀释进主指标。
- 所有查询计划只允许使用用户问题，不允许看到 ground truth、答案、页面标题或完整母库索引。
- LLM 只生成查询计划，不判断实验是否成功；成功由冻结 ground truth 和 outcome grader 判定。
- 任何生产代码切换都不属于本实验。实验候选先实现于 RETRIEVAL-MULTI 专用 eval runner。

## 4. 2×2 因子设计

两个独立因素：

| 因素 | 水平 0 | 水平 1 |
|---|---|---|
| 查询策略 Q | 单查询 | 拆分为 2–3 个互补子查询 |
| 排序策略 R | 生产子串 BM25 直接排序 | 子串 BM25 候选池 + jieba TF-IDF 精排 |

形成四个实验臂：

| 编号 | 查询策略 | 排序策略 | 用途 |
|---|---|---|---|
| A | 单查询 | 子串 BM25 | 当前生产 baseline |
| B | 多查询 | 子串 BM25 | 估计查询拆分主效应 |
| C | 单查询 | BM25→TF-IDF | 估计精排主效应 |
| D | 多查询 | BM25→TF-IDF | 检验组合与交互效应 |

不能先只比较 A 与 D 后宣称某个机制有效；主结论必须来自完整 2×2 对照。

## 5. 公平预算协议

多查询天然会扫描更多文档。如果不固定预算，实验测到的只是“花更多成本通常更好”。因此同时运行两条预算轨道。

### 5.1 等候选预算轨道：主要因果实验

- 每个问题最多生成 3 个查询槽位。
- 单查询臂：1 个查询取 Top-30。
- 多查询臂：最多 3 个查询，各取 Top-10。
- 合并后按路径去重，最多保留 30 个候选。
- 精排臂与非精排臂使用完全相同的 30 个候选集合。
- 最终向 Agent 返回 Top-10，每页摘要字符上限保持 500。
- 同一文档被多个子查询命中时，只计一次候选，但记录命中次数和各查询最高排名。

该轨道用于估计机制效果，不能代表当前生产成本。

### 5.1.1 候选融合与精排公式

为避免运行 test 后再选择有利的融合方式，首版公式预先固定：

- A/C 的单查询候选按生产子串 BM25 原始分数排序。
- B/D 的多查询候选先按 Reciprocal Rank Fusion 合并：`RRF(d) = Σ 1 / (60 + rank_q(d))`；未被某子查询命中的文档不贡献该项。
- RRF 同分时依次按“命中子查询数降序、最佳子查询名次升序、路径字典序”打破平局。
- C 使用原始用户问题与候选文档的 jieba TF-IDF cosine 做精排。
- D 对每个子查询分别计算 TF-IDF cosine，文档最终分数取各子查询分数的最大值；同分时以 RRF 分数和路径字典序打破平局。取最大值是因为必要页面通常只服务一个子问题，取平均会惩罚这种正确的专门化页面。
- TF-IDF 分数只在已经冻结的候选集合内计算，但 IDF 来自当前 manifest 的全部可见页面，不能用 ground truth 或完整母库统计。
- 所有分数使用全精度排序，产物中另存可读的截断值；不得用截断值参与排序。

融合常数、聚合函数和 tie-breaker 只可在 dev 比较一次；如果 dev 选择了不同配置，必须在运行 test 前写入冻结配置及 hash，并在正式报告中说明与本预注册默认值的差异。

### 5.2 真实部署预算轨道：产品决策实验

- A 保持当前一次调用、Top-20 的生产行为。
- 候选方案使用设计所需的真实调用次数和候选数。
- 完整记录扫描页数、排序时间、工具调用、tokens、延迟和成本。

该轨道回答“收益是否值得成本”，不与等预算轨道合并统计。

## 6. 查询计划协议

查询计划统一为结构化 JSON：

```json
{
  "strategy": "single|decomposed",
  "queries": [
    {
      "query": "实体或概念 属性",
      "target": "要找的子事实",
      "entities": ["实体名"]
    }
  ]
}
```

硬约束由代码校验：

- single 必须恰好 1 个查询，decomposed 为 2–3 个；
- 每个查询非空、去重，最长 80 字；
- 计划中不得出现路径、`.md`、`S1`、ground truth 或参考答案片段；
- 查询必须经过与对应检索器一致的规范化；
- 无效输出最多重试一次，仍失败记为 query-plan failure，不用人工计划替换。

prompt 放在 `prompts/evals/`，标注 `llm-weight: medium`。决策策略优先通过 prompt 调整；候选预算、泄漏检查、重试和超时由代码保证。

### 6.1 查询计划的两类评估

为区分“策略上限”和“在线稳定性”，保留两组结果：

1. **冻结计划轨道**：先用 dev 调整 prompt；随后用冻结的 prompt/model/config 分别为 dev 和 test 生成查询计划并保存输入 hash，test 计划生成后不得根据召回结果改写。它测试检索策略本身。
2. **在线计划轨道**：Agent trial 中由相同模型即时生成计划。它测试实际可部署链路，并记录多 trial 方差。

冻结计划不能用 test 指标调参；人工只检查泄漏、子问题互补性和是否偏离用户问题，不根据召回结果修改。

## 7. 任务集

### 7.1 查询数量

在现有 60 条查询基础上构建 RETRIEVAL-MULTI：

- 至少 30 条跨文档查询；
- dev 10 条，test 20 条；
- 每条需要 2–3 个 grade≥2 的必要页面；
- 至少 8 条含近似实体、别名或同领域干扰；
- 至少 6 条要求比较两个实体的同一属性；
- 至少 6 条要求把不同页面事实合成为一个结论；
- 另设 6 条证据不足题，只评估拒答和无依据结论，不进入 Recall 分母。

### 7.2 查询来源与标注

- 优先复用上一轮已有跨文档查询和 judgments。
- 新增查询只能基于冻结 Wiki 内容生成，不能凭模型记忆编造答案。
- TF-IDF、BM25、多查询四臂各取 Top-30 合并候选池，再加入同领域和稳定随机补样。
- 对候选文档标 0–3 级相关性；所有 test 查询进行人工最终复核。
- ground truth 以完整母库为准；每个 controlled 最小子库必须包含全部必要证据。

### 7.3 难度分层

每条查询标记：

- `evidence_count`：2 或 3；
- `entity_overlap`：低/中/高；
- `answer_shape`：并列事实/比较/综合判断；
- `alias_required`：是/否；
- `distractor_density`：完整库中同名或近邻页面数。

报告需按这些层次拆分，避免平均值掩盖机制只对某类任务有效。

## 8. 离线实验

### 8.1 矩阵

- 实验臂：A/B/C/D；
- 规模：50、100、200、500；
- controlled subset seed：5；
- 查询：test 集全部跨文档可回答查询；
- 每个条件使用冻结查询计划；
- 预计条件数：4 × 4 × 5 × 20 = 1,600 个 query-condition。

### 8.2 主要指标

#### Complete Evidence Recall@K

只有当一条查询的全部必要页面都出现在 Top-K 时记为 1，否则为 0。这是本实验的首要离线指标。

同时记录：

- Macro Recall@5/10/20；
- Worst Evidence Rank：必要页面中排名最差者的名次；
- MRR 与 NDCG@5/10；
- 无结果率；
- 候选去重率；
- 每个子查询的边际新增相关证据数；
- 构建、召回、合并、精排各阶段延迟。

### 8.3 统计分析

- 以 query 为主要配对单位，先对同一 query 的 5 个 seed 求均值。
- 对 Complete Evidence Recall 使用 query-cluster bootstrap 95% CI。
- 对 2×2 设计报告：查询拆分主效应、精排主效应和交互效应。
- 同时报告每个 seed 的差值方向；若 5 个 seed 方向不一致，不下稳定结论。
- 只在 dev 集选择子查询上限、候选池大小和 TF-IDF 表示；test 只运行一次正式配置。
- 不因某个 test task 失败而调整 prompt 或参数。

### 8.4 离线晋级门槛

候选进入 Agent 实验必须同时满足：

- test Complete Evidence Recall@10 相对 A 提升至少 10 个百分点；
- 95% CI 下界大于 0，或 5 个 seed 全部同方向且样本量不足以得到窄 CI；
- 单页 Recall@10 不下降超过 2 个百分点；
- 等预算轨道 P95 延迟不超过 A 的 1.5 倍；
- 不增加 manifest 泄漏、零分补位或虚假路径。

若 B 晋级而 C 不晋级，只测试查询拆分；若 C 晋级而 B 不晋级，只测试精排；若 D 的交互收益存在，保留 A/B/C/D 中最小必要集合进入 Agent 阶段。

## 9. Agent 端到端实验

### 9.1 条件选择

首轮固定：

- 规模：50、200、500；
- task：6 条 test 跨文档任务，按 evidence_count、alias_required 和离线差异分层选择；
- baseline A 必须保留；
- 最多保留 2 个离线晋级候选，避免无差别跑完整昂贵矩阵；
- 每个 retriever policy × size × task 至少 3 trials。

若保留 A 加两个候选，最多 3 × 3 × 6 × 3 = 162 trials。先运行每条件 1 次工程 pilot；确认 grader、路径规范化和 trace 正确后，pilot 作废并重新开始正式 3 trials。

### 9.2 固定变量

- 相同模型、temperature、system prompt、agent-loop prompt；
- 相同工具名和返回 schema；
- 相同页面摘要长度和最终 Top-10；
- 相同 max steps、timeout 和 cost budget；
- controlled manifest 固定 seed-1，Agent trial 只测模型波动；
- 条件顺序交错运行，避免时间段或服务状态系统性偏向某一实验臂。

### 9.3 Outcome grader

主要使用确定性 grader：

- 每个必要事实槽位是否被正确覆盖；
- 每个事实是否对应真实且可见的证据路径；
- 全部必要证据是否覆盖；
- 是否引用 manifest 外或不存在路径；
- 证据不足题是否正确拒答。

只有综合判断无法用固定事实槽位表达时才使用 LLM grader，并允许 `uncertain`。LLM grader prompt 必须标注 `llm-weight: heavy`，uncertain 进入人工复核，不自动算成功。

### 9.4 Agent 指标

主要指标：

- 完整任务成功率；
- 事实覆盖率；
- 证据覆盖率；
- 无依据结论率；
- 虚假/不可见路径率。

辅助指标：

- 首次召回即覆盖全部证据的比例；
- query plan failure rate；
- 重试次数、steps、工具调用；
- prompt/completion tokens、成本和延迟；
- 同一条件 3 trials 的方差。

trace 用于解释失败发生在查询计划、候选召回、精排、证据读取还是最终回答，不以固定工具路径作为成功条件。

## 10. 决策规则

### 10.1 查询拆分机制

仅当 B 相对 A 在 test Agent outcome 上满足以下条件，才保留查询拆分：

- 跨文档成功率绝对提升 ≥10 个百分点；
- 证据覆盖率提升 ≥10 个百分点；
- 至少 5/6 个 task 的差值方向非负；
- 无依据结论率不升高；
- 平均成本不超过 A 的 2 倍，P95 延迟不超过 2 倍。

### 10.2 精排机制

仅当 C 或 D 相对对应非精排臂稳定提高 Agent outcome，且收益不是只体现在 NDCG 时，才继续产品化。离线 NDCG 提升但 Agent outcome 无变化，不切换。

### 10.3 组合策略

- D 显著优于 B 与 C：保留组合，进入更大 task 集复验。
- B 与 D 相当：删除精排，只保留更简单的查询拆分。
- C 与 D 相当：删除查询拆分，只保留精排。
- 所有候选只改善离线指标：不改生产，记录机制未传导。
- 不同 task 或 seed 方向冲突：扩大跨文档查询集，不下全局结论。

稳定通过 50/200/500 页且连续两次独立运行无回退的任务，才考虑进入 regression suite；其余继续留在 capability suite。

## 11. 失败分类与诊断

每个失败必须归入一个主要阶段：

1. `plan_invalid`：查询计划格式错误、泄漏或重复；
2. `query_miss`：子查询未命中必要页面；
3. `merge_loss`：命中后在去重/合并时丢失；
4. `rerank_loss`：候选含证据，但精排挤出 Top-10；
5. `agent_ignored`：工具返回证据但 Agent 未使用；
6. `answer_incomplete`：事实不完整；
7. `evidence_invalid`：事实正确但路径错误或不可见；
8. `unsupported_claim`：输出来源未支持的额外结论；
9. `runtime_failure`：超时、模型错误或工具错误。

分类优先由 trace 和确定性状态推导；同一 trial 可记录次要原因，但只指定一个主要失败阶段，便于聚合。


每个运行记录：

- corpus version/hash；
- manifest path/hash；
- query-plan prompt/model/hash；
- 四臂配置和候选预算；
- 每个子查询的 ranked list；
- 合并前后候选及精排分数；
- 最终返回页面；
- Agent trace、usage、成本、延迟和 grader 结果。

缓存必须绑定所有输入 hash；改变 prompt、模型、语料、manifest 或参数时不得复用旧缓存。
