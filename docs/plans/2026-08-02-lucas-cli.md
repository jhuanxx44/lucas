状态：规划（讨论稿，未开始实施）

## 0. 背景与目标

现状：Lucas 只有 Web 一套外壳——React 前端 + FastAPI/SSE 后端。核心 Agent 循环（`harness/AgentRunner`）本身已经是纯 async Python、对 Web 零依赖，所有 Web 耦合集中在 `server/services/agent_stream.py` 一个文件（AgentRunner → SSE 翻译层）。

目标：新增 **lucas-cli**——完全本地运行的终端外壳，与 Web 共享同一个业务内核，形成：

```
lucas-core（业务内核）→ lucas-web（薄壳）+ lucas-cli（薄壳）
```

**范围澄清**：「完全本地运行」指 CLI 界面 + 本地数据，LLM 仍默认调 DeepSeek API。「连模型也本地跑」（Ollama/vLLM）是独立的可选方向，见第 6 节，不在本规划主线内。

**非目标**（明确不做）：

- 不拆物理发行包（lucas-core / lucas-cli / lucas-web 三个 distribution）——先保持单仓库单包、逻辑分层，有真实分发需求再拆。
- 不做本地模型适配（独立立项，需 eval-driven 验证，见第 6 节）。
- 不做命令工具与沙箱（独立立项，见 `docs/plans/2026-08-04-tool-runtime-安全边界.md`）。
- 不做多用户（`user_id` 恒 default 维持现状）。
- 不为 CLI 重写 harness；AgentRunner 行为不变是硬约束（M6 加 confirm 回调除外）。

## 1. 现状盘点：哪些已解耦，耦合在哪

```
web/          React 前端（聊天、wiki 浏览、Trace 面板）        ← CLI 整体替换
server/       FastAPI + SSE 桥 + 会话/知识路由                 ← 大部分被替换
  ├ services/agent_stream.py   Runner → SSE 翻译（541 行）     ← 需拆解
  ├ services/session_store.py  JSON 会话存储                   ← 直接复用
  └ services/knowledge.py      wiki ingest/compile 管线        ← 直接复用
harness/      AgentRunner / ModelAdapter / ToolRuntime / Trace ← 不动
utils/        llm_client、web_search、stock、wiki_core         ← 不动
workspace.py  LocalWorkspace（写死项目根、单用户 default）     ← 小改
scripts/      20+ 个 wiki 批处理脚本                           ← 已是 CLI 形态
```

关键事实：`AgentRunner.run()` 通过 `on_event`/`on_trace_event` 回调吐结构化事件，不 import 任何 Web 组件。

### 1.1 core 已经泄漏了，泄漏对象不是 CLI 而是 eval

「两边各写一遍后一样的代码就是 core 漏出去了」这条判定**今天已经成立**，第二个壳是
`evals/harness/adapters/lucas_single.py`：

| 装配职责 | agent_stream.py | lucas_single.py |
|---|---|---|
| 读 lucas.yaml / 环境变量覆盖 | 有 | 有（多一层 env 覆盖） |
| 拼 tool spec 列表 | 有（10 个） | 有（10 个，write 无 guard） |
| prompt 路径定位 | `_PROMPT_PATH` | `PROMPT_PATH` |
| system prompt + create_client + ResponsesModelAdapter | 有 | 有 |

由此带来一个比「想做 CLI」更重要的问题：**Agent 级 eval 现在测的不是生产装配。** 生产的
`write_file` 经 `_guard_wiki_write` 收窄，eval 里是裸 `WRITE_FILE_SPEC`。`evals/tasks/README.md`
把这个差异记为「有意的」——在工具面上确实有意（要覆盖框架级文件能力），但 CLAUDE.md 对
Agent 级 eval 的要求是「被测对象一定是生产实现」，policy 层这一块目前不满足。

因此 M3 的 policy profile 不是为 CLI 造的推测性灵活性，而是**三个已存在的消费者**
（web / eval / 未来 cli）各自选 profile，即使 CLI 永远不做也该修。

另一条已有保障：`tests/test_chat_sse.py`（396 行）已覆盖事件序列、工具轮中间文本丢弃、
断连取消、trace 落盘，M1 的回归有它兜底。

`chat_event_stream` 目前混合了四类职责，拆解时按此分类：

| 职责 | 归属 |
|---|---|
| 装配（配置、工具白名单、wiki 写 guard、prompt 组装、日期头、寒暄判断） | core |
| 驱动（启动 runner、消费事件队列、按 turn 缓冲答案、区分工具轮中间文本） | core |
| SSE 序列化、打字机冲洗节奏 | web 壳（纯展示策略） |
| 中文错误文案、trace 落盘 | core |

判断归属的标准：**web 和 cli 各写一遍后，两边一样的代码就是 core 漏出去了。**

## 2. 目标架构

### 2.1 三层划分

```
lucas-core（不 import 任何 shell）
├── harness/          AgentRunner / ModelAdapter / ToolRuntime / Trace   ← 已解耦
├── chat 内核          run_chat() → 结构化事件流                          ← 从 agent_stream.py 抽出
├── knowledge.py      wiki ingest/classify/compile 管线                  ← 已解耦
├── session_store.py  会话存储（web/cli 共享）                            ← 已解耦
├── policy 层          权限策略（白名单 / 作用域守卫 / 确认回调）          ← 新，见 3.2
│                      三个消费者共用：web / eval / cli
├── workspace.py      路径抽象（支持 --workspace / LUCAS_HOME）           ← 小改
└── config + prompts  lucas.yaml、prompts/ 加载（改为包内资源定位）       ← 小改

lucas-web（薄壳）      FastAPI 路由、SSE 序列化、React 前端
lucas-cli（薄壳）      typer 命令、rich 渲染、REPL、Ctrl-C 取消、交互确认
```

### 2.2 core 与壳的契约：结构化事件流

`run_chat(question, history) -> AsyncGenerator[dict]` 吐出的事件（`tool_start` / `tool_step` / `thinking_chunk` / `answer_chunk` / `context_usage` / `context_compressed` / `plan_update` …）就是 core 对外的 API。web 壳序列化成 SSE，cli 壳渲染到终端。

协议稳定后两套壳独立演进；前端 Trace 面板和 CLI 看到的过程天然一致，CLAUDE.md 第 6 节的两类 trace 关联自动继承。

### 2.3 打包形态

单仓库、单包、两个入口：

```toml
[project.scripts]
lucas = "cli.main:app"          # CLI
lucas-web = "server.app:main"   # Web 服务
```

「lucas-core + 双壳」是**逻辑分层**（core 不许 import server/cli，可用 import-linter 或测试强制），物理分包等真正有分发需求再做。

## 3. 关键设计决策

### 3.1 会话存储放 core，两壳共享

SessionStore 留 core，不要在两套壳各实现一遍。实质收益：web 里聊了一半的对话，CLI 里 `lucas --resume` 接着聊，历史注入逻辑（`_render_history`）也只有一份。

现在会话生命周期由前端通过 HTTP 驱动（create/rename/replace_messages），CLI 要自持：启动时建/续会话，每轮结束 append messages。

### 3.2 权限模型：policy 层进 core，四层可组合

不能把权限做成「web 一套、cli 一套」两个硬编码。真实消费者已有三个（web / eval / cli，见
1.1），要泛化为 core 里的 policy 层。四层独立生效、可组合：

```
L1 工具白名单    allowed_tools（已有，lucas.yaml）
L2 作用域守卫    写路径收窄、raw/ 禁写、命令黑名单 → 代码强制
L3 交互确认      高危操作前停下来问用户（M6，见 3.3）
L4 沙箱          OS 级隔离，限制爆炸半径（独立立项，见 3.4 末尾）
```

- L1/L2 必须由代码保证（CLAUDE.md 不可违反约束：执行语义、安全、权限不只写进 prompt）。**raw/ 禁写继承到所有壳**，它是项目级不可违反约束。
- 实现沿用现有 `_guard_wiki_write` 的「包装 tool handler」模式，泛化为 guard 链：ToolRuntime 注册时按 profile 应用。**策略定义放 core，profile 选择放壳。**
- profile：web = 研究工具白名单 + wiki-only 写（现状）；cli = 同样 wiki-only 写（见 3.4）+
  高危操作确认；eval = 全工具注册 + 生产 policy，逐题由 `task.yaml` 的 `allowed_tools` 收窄。

### 3.3 确认回调：与终端交互一起做（M6），不提前冻结

L3 确认要求工具执行前壳能「问用户要一个 y/n」，即壳 → core 的反向通道。现在 `run_chat`
事件流是单向的（core → 壳），需要给 `AgentRunner.run()` 加确认回调：

```python
confirm: Callable[[ConfirmRequest], Awaitable[bool]]  # runner 在高危工具执行前 await 它
```

**不在 M2 用哑实现提前冻结签名**，理由：

- 第 7 节开放问题 3 本身就承认还不知道 `ConfirmRequest` 该带哪些字段。没有真实调用方时
  冻错概率高于冻对，而哑实现不会暴露任何设计错误——这也与「不增加没有被要求的灵活性」
  「不为单次使用创建抽象」冲突。
- 没有交付压力：confirm 服务 L3，L3 服务的高危工具在 M6。M4/M5 靠 L1 白名单 + L2 作用域
  守卫就够，deferring 成本接近零。
- `run()` 现已有 `trace / on_event / on_trace_event / stream_answer` 四个可选参数，confirm
  是第五个。真要动这个签名，值得同时考虑收成一个 hooks 对象而非继续追加——这个判断也需要
  真实的第二、第三个调用方才做得准。

因此 confirm 与终端交互在 M6 一起落地，由真实调用方定义结构。

### 3.4 CLI 的工具面

- 写入策略与 web 一致，保持 wiki-only：L2 一份实现三处共用（web / eval / cli）。
- wiki 子命令（`lucas wiki ingest/compile`）直接调 knowledge.py——scripts/ 里已有大量 CLI
  形态先例。
- 命令工具（`run_tests` / `shell_info` / 或通用 `run_command`）与沙箱**不在本规划内**，见
  `docs/plans/2026-08-04-tool-runtime-安全边界.md`。它们的验收全是确定性 grader，注册进
  eval adapter 即可验证，不需要 CLI；反之 L3 确认在无人值守的 eval 里没有意义。两条线在
  M6 汇合——届时工具已存在，CLI 只需选 profile。

### 3.5 工作区定位：定 B（`~/.lucas`）

原备选：A 仓库即数据家（零迁移，只能当开发工具用）／B `~/.lucas` 用户级／C `lucas init`
项目级（类 git，每目录一套 wiki）。**定 B**，依据：

- `wiki/`、`raw/`、`memory/` 均已在 `.gitignore`（`git ls-files` 对三者都是 0），数据与代码
  逻辑上已分离，只是物理同目录。迁移成本 = 一次 `mv`（41M raw + 7.1M memory/sessions）。
- C 的动机是「不同目录研究不同主题」，该需求未在任何地方被提出——Lucas 是单一 A 股知识库，
  按简单优先属推测性功能。
- **B → C 是增量而非破坏性变更**：C 只是在同一 Workspace 抽象上多一种解析策略（向上找
  `.lucas/`）。先 B 不堵死 C。
- 路径覆盖已有先例可沿用：`LUCAS_CHAT_TRACE_DIR` 是环境变量覆盖模式（`LUCAS_HOME` 同构），
  显式传入 root 的通道也已存在（`evals/harness/workspace.py` 的 `TrialWorkspace`）。

另外 prompt 路径（`harness/config.py`、`agent_stream._PROMPT_PATH`、
`runner.SUMMARY_PROMPT_PATH`）目前是仓库相对路径，打包后须改为包内资源定位，不依赖 CWD。

## 4. CLI 壳设计要点

- **两种模式**：一次性 `lucas "问题"`；交互式 `lucas`（REPL，多轮带历史）
- **渲染映射**（事件 → 终端）：
  - `tool_start`/`tool_step` → 状态行（`⠋ 调用 web_search: 茅台年报`）
  - `thinking_chunk` → 暗色流式
  - `answer_chunk` → **必须按 turn 缓冲，不可直接上屏**。工具轮也会流式吐
    `output_text.delta`，唯一可靠信号是 turn 完成时是否含 function_call，runner 因此在工具轮
    发 `answer_discard`（见 `docs/lessons/2026-08-01-responses工具轮流式中间文本.md`）。直接
    上屏会让用户看到「知识库里没有记录，我联网查一下」这类中间叙述，且终端上屏后擦不掉，
    比前端更糟。与 web 的真实差异只有一句：web 假装打字机，CLI 缓冲结束后一次 print——不存在
    「终端天然支持所以更简单」。
  - `plan_update` → 步骤清单；`context_usage` → 底部一行
  - Markdown 用 rich 渲染（表格、代码块）
- **取消**：Ctrl-C → cancel run task（对应服务端「客户端断开即取消」语义）
- **trace**：复用 TraceRecorder 落盘（`LUCAS_CHAT_TRACE=1` 不变）

```
M3  policy/guard 泛化进 core；web / eval / cli 各选 profile
    验收：wiki-only 写限制回归通过；eval adapter 走生产 policy（修 1.1 的保真度缺口）
M4  cli 壳最小闭环：一次性问答 + 终端渲染（含 answer 缓冲）+ trace 复用
    验收：lucas "问题" 端到端跑通；工具轮中间文本不上屏；trace 与 web 同构
--- 此处停下评估，再决定下面做不做 ---
M5  REPL + 会话持久化（复用 SessionStore，--resume）
    验收：web 建的会话能在 cli 续聊

    验收：高危工具需确认才执行；raw/ 禁写测试通过

    验收：pipx install 后任意目录可用
--- 独立立项 ---
    Tool Runtime 超时/取消 + 命令工具 + 沙箱：见 2026-08-04-tool-runtime-安全边界.md

```

原 M2（confirm 哑实现）已删除，合入 M6，理由见 3.3。

M1/M3 是纯收益重构：即使最终不做 CLI，把 SSE 从业务逻辑里剥出来、让 policy 层显形并修掉
eval 保真度缺口，本身就该做。任何一步失败可停下，不留半成品。

### 5.1 成功标准与「成功了也可以停」

CLI 的真实价值是**harness 开发工具**：不起 FastAPI + vite 就能跑一轮完整 agent loop，改
prompt 后的迭代循环从几十秒变几秒，trace 立即可读。按此标准：

- **M4 已拿到这份价值的绝大部分。**
- M5（跨壳续聊）、M7（打包 + 工作区迁移）边际价值低得多，M7 还是整条路径里最有破坏性的
  一步。跨壳续聊听起来漂亮，但需要先确认真会在 CLI 里接着 web 聊到一半的对话。

因此 M4 之后设一个明确的评估点：用一段时间，再决定 M5 起做不做。

## 6. 可选方向：本地模型（独立立项）

「完全本地」若含本地推理（Ollama/vLLM），额外需要：

- **新 ModelAdapter**：本地推理服务基本只兼容 Chat Completions，不支持 Responses 协议，需在 `harness/model_adapter.py` 旁加 chat.completions → ModelTurn 归一化层。
- **能力风险**：现有 prompt 栈（agent-loop.md、并行工具调用、context 压缩）按 deepseek-v4 级 function calling 能力调试，换本地小模型后工具调用可靠性预计明显下降。按项目规范这属于 Agent 机制变化，须走 eval-driven 流程（baseline → 最小改动 → 多 trial 对比）验证。
- **外部工具降级**：web_search、stock_quote/kline 依赖外部 API，「完全本地」要么禁用要么换本地数据源；wiki_recall/read_file/search 本来就是本地的。
