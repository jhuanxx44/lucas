# 用「模型生成的摘要」替代原生 reasoning 草稿展示

## 问题：为什么过程展示全是重复废话

聊天区的过程展示原本直接渲染模型的**原生思考通道**（`reasoning_content`）。
在 ReAct 循环里，模型是无状态的：每一轮我们都把完整的 `{任务} + {历史观察}` 重新拼进
prompt 喂给它。于是模型每一步都从「我们被问到 X…需要对比…先检查知识库…」重新热身一遍，
trace 里每段思考开头高度雷同、冗长。

对比 Codex，它展示的每一句都简短有用（「我会把这根线做成双轴趋势图」「测试 68/68 通过」）。
关键差异不在模型聪明与否，而在**展示的是什么**：

| | 原生 reasoning | 用户摘要 |
|---|---|---|
| 来源 | 模型的思维草稿（自言自语） | 模型**另外生成**的、写给人看的一句话 |
| 风格 | 反复热身、啰嗦 | 简短、像同事汇报 |
| 用途 | 内部推理 | 展示 |

Codex 靠 OpenAI Responses API 的结构化 items 天然分离思考与消息。我们没有那层结构，
但可以用更简单的办法达到同样效果。

## 方案：让动作 JSON 自带一句 summary

核心判断：**摘要不是新的通道，而是动作协议里的一个可选字段。**

模型每轮本来就要输出一个 JSON 决定动作（`{"action":"tool"/"answer", ...}`）。我们只在
它前面加一个可选的 `summary` 字段：

```json
{ "summary": "查一下知识库里有没有这家公司的档案",
  "action": "tool", "tool": "wiki_recall", "args": {...} }
```

- **展示**：runner 解析出 action 后、执行工具前，把 summary 作为 `summary` 事件发给前端。
- **草稿**：模型原生 reasoning 仍然产生，但 SSE 层不再转发前端，只留在 trace 文件里供调试。
- **动作**：`action/tool/reply` 的语义完全不变。

## 为什么这样最省事、最安全

1. **对解析零风险**。`_parse_action` 只读它认识的键，`summary` 是多出来的字段，天然被忽略；
   流式答案解析器 `AnswerStreamParser` 的正则只认 `"reply":` 和 `"action":"tool"`，前置的
   `summary` 不影响判定。所以不需要碰任何解析核心，也不需要引入分隔符。
2. **不动执行语义**。summary 只是一次 `on_event` 回调，工具执行、预算、超时、重试全不受影响。
   eval 走非流式路径时也会解析到 summary，但不消费该事件，无副作用。
3. **向后兼容**。历史会话里旧的 `thought` 步仍按旧样式渲染，不破坏老数据。

## 一个流式顺序的取舍

流式模式下，answer 步的 `reply` 是边解析边逐字推送的，而 `summary` 要等整段 JSON 到齐才解析。
所以对**答案步**，summary 事件会晚于答案 chunk 到达。这看似别扭，但两者渲染在不同 UI 区域
（摘要在分析过程区、答案在气泡里），先后无所谓；而对**工具步**，summary 一定先于工具动作
（测试保证）——那才是「先说要做什么，再做」的关键 UX。因此没有为这个顺序增加任何缓冲复杂度。

## eval 验证（CLAUDE.md 要求）

这是改动了输出契约的 Agent 机制实验，走 eval-driven 流程，主指标是任务成功率不回归。

business-capability 套件（WIKI-01/02/03），DeepSeek，各 3 试：

| | 成功率 | 说明 |
|---|---|---|
| baseline（无 summary） | 9/9 = 100% | 还原 prompt 后跑 |
| variant（有 summary） | 9/9 = 100% | 无回归 |

- summary 覆盖率：34/37 步 = 92%（缺的 3 步是无 action 外壳的裸 JSON 答案，符合预期）。
- 实际产出样例：「查一下知识库里有没有澄海精密的相关信息」——简短、口语、无重复热身，
  达到了 Codex 那种观感。

结论：保留该机制。

## 关键取舍回顾

- **为什么不折叠原始草稿**：那是治标，展示的仍是草稿；生成摘要才是治本。
- **为什么不用分隔符 / 原生 tool_calls**：现有文本 JSON 协议工作正常，加一个可选字段是
  改动面最小的方案，不值得为此重构协议。
- **为什么草稿不彻底关掉**：模型原生 reasoning 对调试仍有价值，留在 trace 文件里，只是不进前端。
