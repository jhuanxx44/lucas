# LLM 关键词 vs jieba 分词检索对照实验

**日期**：2026-07-26  
**状态**：已完成  
**关联 commit**：`6bf12cc`

---

## 1. 实验目标

围绕 `wiki_recall` 的生产链路，回答两个问题：

1. **用 LLM 提取中文关键词再检索，是否优于 tool 内部 jieba 分词？**
2. **在 LLM 关键词前提下，TF-IDF 和 BM25 哪个更适合当前语料规模？**

在上一轮 BM25 对照实验中发现：查询集的 `keywords` 字段（人工编写的实体名和专业术语）检索效果远好于自然语言输入（TF-IDF 从 R@5=0.650 跳到 0.882）。但这批 keywords 是人工精心挑选的，不能代表真实 LLM 行为。

本实验用真实 LLM（DeepSeek-Chat）对每条自然语言 query 实时提取关键词，在生产链路和 eval 检索引擎上同时验证。

---

## 2. 实验设计

### 2.1 生产链路对照（轮次一）

对比 `recall_wiki` 的两个 mode，使用相同的 wiki 文档和 BM25 索引：

| 路径 | 输入 | 检索引擎 | 关键词来源 |
|------|------|:--------:|------------|
| NL（jieba） | 自然语言问题 | production BM25 | `extract_keywords()` — jieba 分词 + 词性过滤 |
| KW（LLM） | 自然语言问题 | production BM25 | LLM 实时提取 → 空格拼接 → `mode="keywords"` |

### 2.2 Eval 检索引擎全覆盖（轮次二）

在轮次一得出 LLM > jieba 后，将 LLM 关键词缓存到 `queries.json`，在 eval 的独立检索引擎上跑完整的 2×2 矩阵：

| 关键词来源 | 检索引擎 | 说明 |
|-----------|:--------:|------|
| LLM（DeepSeek-Chat） | BM25 | 默认模式，匹配生产链路 |
| LLM（DeepSeek-Chat） | TF-IDF | 探索更优引擎组合 |
| 人工 | BM25 | 手工关键词理论上限 |
| 人工 | TF-IDF | 手工关键词 + TF-IDF 最优组合 |

### 2.3 共享条件

- **模型**：`deepseek-chat`，System Prompt 要求提取实体名/专业术语，3-8 个关键词空格分隔
- **回退**：LLM 调用失败时回退到 jieba（本次实验 0 次回退）
- **查询集**：15 条自然语言 query，覆盖公司事实/概念解释/跨文档综合/干扰查询
- **语料**：46 篇 wiki fixture（半导体 + 光通信 + 多行业干扰项）
- **评估**：确定性 grader（R@5 / P@5 / MRR / NDCG@5）

## 3. 实验结果

### 3.1 生产链路：LLM 关键词 vs jieba（BM25 引擎）

```
Mode                                R@5      P@5      MRR   NDCG@5
----------------------------------------------------------------
NL (jieba → production BM25)      0.4789   0.3333   0.7074   0.4958
KW (LLM  → production BM25)       0.6911   0.4833   0.8667   0.6894
```

**LLM 关键词全面碾压 jieba**：R@5 +0.212，MRR +0.159。DeepSeek-Chat 15 次调用零失败。

### 3.2 Eval 检索引擎全覆盖（LLM vs 人工，BM25 vs TF-IDF）

```
模式                                    R@5      P@5      MRR   NDCG@5
------------------------------------------------------------------------
LLM-KW + BM25（默认/生产）               0.6589   0.4567   0.7417   0.6254
LLM-KW + TF-IDF                    0.7167   0.4667   0.7389   0.6621
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
人工 KW + BM25（理论上限）                 0.8267   0.5600   0.9667   0.8468
人工 KW + TF-IDF（理论上限）               0.9156   0.6267   1.0000   0.9332
```

关键发现：

- **用 LLM 关键词后，TF-IDF 依然优于 BM25**（R@5 差 0.058）。趋势与上一轮 BM25 对照实验一致：46 篇语料对 BM25 还是太小，IDF 主导的 TF-IDF 更适配当前规模。
- **LLM 离人工上限的差距 ≈ 0.17 R@5**（BM25 上 0.659 vs 0.827）。这个 gap 不是检索引擎能填的，只能在 LLM 关键词提取 prompt 上优化。
- eval 检索引擎的 BM25 数字（0.659）略低于 production `recall_wiki` 的 BM25（0.691），是因为 eval tokenizer 缺少 production `_tokenize_doc` 的专有名词补充。

### 3.3 按查询类型（LLM-KW + BM25）

| 查询类型 | jieba R@5 | LLM-KW R@5 | Δ |
|----------|:---------:|:----------:|:---:|
| 公司事实 (q01-q04) | 0.567 | 0.733 | +0.167 |
| 概念解释 (q05-q08) | 0.625 | 0.792 | +0.167 |
| 跨文档综合 (q09-q11) | 0.511 | 0.689 | +0.178 |
| 干扰查询 (q12-q15) | 0.208 | 0.500 | +0.292 |

干扰查询受益最大（+0.292）：LLM 提取的关键词如"电动汽车/续航里程/充电速度"不会像 jieba 那样切出"技术""突破"等通用词，避免了大量半导体文章被误召回。

## 4. LLM 关键词提取质量分析

### 典型优秀案例

**q01**（全球晶圆代工市场参与者）：
- jieba：`['全球', '代工', '市场', '参与者', '工艺水平', '竞争', '定位']`
- LLM：`['全球晶圆代工', '市场', '主要参与者', '工艺水平', '竞争定位']`
- 差异：LLM 保留了"全球晶圆代工"作为完整术语，识别出"竞争定位"这类复合概念

**q09**（芯片从设计到成品的环节）：
- jieba：`['设计', '成品', '芯片', '经历', '核心', '环节']`
- LLM：`['芯片', '设计', '成品', '核心环节', '制造', '封装', '测试']`
- 差异：LLM 展开了"核心环节"的具体内容（制造/封装/测试），检索精准度不在一个量级

### 典型不足

**q01**（第一轮提取 vs 缓存版差异）：
- 轮次一：`['全球晶圆代工', '晶圆代工市场', '主要参与者', '工艺水平', '竞争定位', '台积电', '三星', '英特尔']`
- 缓存版：`['全球晶圆代工', '市场', '主要参与者', '工艺水平', '竞争定位']`
- 同一模型、同一 query 的两次提取结果不一致（缺少了"台积电/三星/英特尔"实体名），说明关键词提取存在随机性

**q07**（波分复用技术）：
- LLM：`['波分复用', '光纤', '多路信号', '同时传输']` — 两次均缺 "WDM" 缩写
- 人工：`['波分复用', 'WDM', '光纤', '多路信号', '同时传输']`
- 缩写丢失是 LLM 提取的持续短板

## 5. 结论与行动

### 核心结论

1. **LLM 关键词碾压 jieba**（R@5 +0.21），根本原因是 jieba 只能做字面分词，LLM 能填平"自然语言 → 检索关键词"的语义鸿沟
2. **TF-IDF 在小语料上持续优于 BM25**，与关键词来源无关（LLM/人工均如此）
3. **LLM 关键词提取存在随机性**（同一 query 两次提取结果不同），prompt 还有优化空间，距人工上限约 0.17 R@5

### 已执行的行动

1. **删除 NL 路径**：`wiki_core.py` 移除 `extract_keywords()` / `_STOP_WORDS` / `search_wiki`，`recall_wiki()` 固定为纯关键词模式
2. **eval 默认接入 LLM 链路**：`queries.json` 缓存 LLM 关键词，`retriever.py` 默认 `mode=llm + retriever=bm25`，匹配生产行为
3. **截断上限收紧**：无 summary 时回退正文从 3000 字符改为 500 字符

### 后续方向

- LLM 关键词提取 prompt 优化（引导输出实体名、缩写、同义词），目标是缩小与人工上限的 0.17 R@5 差距
- 扩库后重新对照 TF-IDF vs BM25，确定切换阈值
- 关键词提取的确定性研究（temperature / few-shot / 结构化输出）
