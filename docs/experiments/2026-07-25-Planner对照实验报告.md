# Planner 对照实验报告

> 2026-07-25 · `planner-experiment-v1` · agent=lucas-single · trials=3 · model=deepseek-v4-flash

## 实验设计

对 4 个 eval task（MULTI-01、MULTI-02、READ-02、LOOP-01）各运行 3 次 trial，测量成功率、步数、plan_usage 调用次数和成本。实验组使用当前 prompt（含 plan 规则），`update_plan` 工具已注册但非强制。

对照组的"无 plan 约束"未单独跑——因为实验组中模型**根本没有使用 `update_plan`**，天然构成了事实上的对照组。

## 分析

### 为什么模型不用 Planner

4 个 eval task 的结构足够简单，线性策略就是最优解：

- **MULTI-01**（跨文件数据汇总）：list_files → read_file × 4 → answer
- **MULTI-02**（Wiki 多公司调研）：wiki_recall → write_file → answer
- **READ-02**（长文导航定位）：read_file × 5–7（目录定位 + 夹逼查找） → answer
- **LOOP-01**（不存在公司兜底）：wiki_recall → answer

模型在这些任务中不需要显式规划，因为任务结构本身已经告诉它"该干什么"。

### 对比手动测试

手动测试的 scenario-01（光通信行业调研：调研 3 家公司 → 写 wiki → 写行业对比报告，17–27 步）中，模型使用了 3–5 次 `update_plan`。那类多阶段、跨文件依赖的任务才是 Planner 能产生差异的场景。

### 核心结论

**Planner 基础设施（工具/SSE/前端/eval）是可用的，但当前 eval task 集的复杂度不足以区分"有 Planner"和"无 Planner"。** 这不是 Planner 实验失败——是 task 集覆盖不到 Planner 能发挥价值的复杂度区间。

## 启示

1. **Eval task 的设计决定了机制实验的区分度**。简单线性任务测不出规划能力，需要多阶段依赖（数据收集 → 中间产物 → 汇总输出）的 task 才能暴露有无 Planner 的差异。
2. **"模型不用工具"不等于"工具没用"**。模型不用 plan 是因为这些任务不需要——这正是好的 Agent 行为（不过度设计）。
3. **要验证 Planner 价值，需要至少一个 15+ 步、多阶段依赖的复杂 eval task**。但这会显著增加 eval 运行成本（READ-02 已是 $0.27/trial，更复杂的 task 可能 $0.5–1.0/trial）。

## 后续决策

- **不为验证 Planner 而新增 eval task**。当前 Planner 基础设施稳定，等后续遇到自然需要规划能力的业务场景时再接入 eval。
