# PLAN-01～04 Pro 模型 Pilot

日期：2026-07-30
Suite：`planner-all-experiment-v1`
Variant：当前 `lucas-single`（Optional Planner）
模型：`deepseek-v4-pro`，temperature=0
Trials：每题 1 次

## 实验边界

本轮保持 PLAN-01～04 当前 instruction、fixture、grader、工具、system prompt 和预算不变，只把模型
从默认 `deepseek-v4-flash` 覆盖为 `deepseek-v4-pro`。模型覆盖只在运行进程内生效，没有修改
`lucas.yaml` 或生产默认配置；四份 `result.json` 均记录实际模型为 `deepseek-v4-pro`。

当前题面并不完全同质：PLAN-01/03 是公开完成态的自然目标任务；PLAN-02 是一句开放目标 probe，
旧 grader 仍绑定固定报告名；PLAN-04 是使用语义报告发现的正式投研任务。因此 raw success 不能直接
作为四题统一能力分数，需结合环境和 trace 做语义复核。

## Planner 路由与时机

| Task | 场景 | Planner | 时机 | 后续更新 |
|---|---|---:|---|---:|
| PLAN-01 | 工程迁移 | 0 | — | — |
| PLAN-02 | 三公司季度对比 | 1 | 第 11/18 步，全部读取后、首次写入前 | 0 |
| PLAN-03 | 事故处置 | 0 | — | — |
| PLAN-04 | 投委会横向研究 | 1 | 第 12/15 步，三份公司页写完后、报告写入前 | 0 |

Pro 只在两道多公司投研题触发 Planner，工程迁移和事故处置均不触发。这与当前 system prompt 只用
“系统调研行业、对比多家公司”说明 Planner 的特化路由高度一致；模型并没有把多文件、依赖、条件
行动和证据覆盖统一识别为规划信号。

两次 Plan 都只调用一次，没有按 system prompt 在阶段完成后更新状态。PLAN-02 的五个步骤全为
`pending`；PLAN-04 的 Plan 只覆盖报告、索引和最终回答，因为三份公司页已经写完。

## 分题归因

### PLAN-01：无 Planner 也完整通过

Pro 正确筛选三个待迁移服务，保留无关配置，生成一致的部署/验证/回滚文档。说明在依赖清晰、规则
明确的任务中，显式 Planner 不是完成 outcome 的必要条件。

### PLAN-02：Planner 改善交付，但遗漏具体来源

Pro 在写入前已读取三份来源、三份旧公司页、索引和旧报告，随后建立公司页、报告、索引五步计划。
它正确保留三家公司原风险，没有重复上一轮 Pro 未读旧页、编造 Q2 数据的问题；报告和索引也真实
落盘。

真实失败是三份公司页没有具体 source path，报告也只引用 `sources/2026Q3/` 目录，无法把关键
数字追溯到具体文件。raw grader 的固定“公司对比”文件名和 allowed_diff 还额外误伤了模型选择的
合理“横向比较”文件名，但不影响来源追溯仍然失败的结论。

### PLAN-03：无 Planner，语义 outcome 通过

Pro 读取发布记录、指标、两份日志、runbook 和配置，正确修改 checkout-api 与 order-worker，保持
inventory-api 不变，并完整写入证据、验证命令和逆序回滚。修正标题正则后全部 outcome 通过。

### PLAN-04：Planner 太晚，真实可靠性失败

Pro 只读取曜川电源旧档案，便覆盖写入三家公司页面；澜岳储能和衡星电气的既有风险因此丢失。
第 12 步才创建 Plan，内容只剩报告、索引和最终回答。报告创建后，第 14 步输出无法解析为合法动作，
第 15 步直接回答；`wiki/index.md` 没有修改，但最终回答声称“已添加报告入口”。

公司页和报告同样没有具体来源路径。这里同时出现了计划过晚、成功条件覆盖不足、无状态更新和虚假
完成声明，说明一次 Plan call 不能代表 Planner 真正发挥作用。

## 与当前 Flash 运行的方向性比较

取四题当前题面最近一次 Flash trial 作为参照：PLAN-01/03 使用自然目标 Pilot，PLAN-02 使用极简
题面 Pilot，PLAN-04 使用修正后正式 trial。它们不是交错运行的多 trial 实验，只作方向性观察。

| Metric | Flash | Pro | 变化 |
|---|---:|---:|---:|
| 语义 outcome | 1/4 | 2/4 | +1 task |
| plan calls | 1 | 2 | +1 |
| steps | 56 | 58 | +3.6% |
| tool calls | 52 | 53 | +1.9% |
| tokens | 241,660 | 267,717 | +10.8% |
| cost | $0.707710 | $0.845454 | +19.5% |
| duration | 224.97s | 574.42s | 2.55x |

- PLAN-01：两模型均 pass、均 0 Planner；Pro 步数和 token 更少，但耗时更长。
- PLAN-02：Flash 0 Planner 且漏报告/索引；Pro 1 Planner 并补齐二者，但两者都漏具体来源。
- PLAN-03：Flash 漏发布记录导致真实失败；Pro 无 Planner 仍完整通过，提升不能归因 Planner。
- PLAN-04：Flash 和 Pro 都调用一次 Planner、都因来源追溯失败；Flash 真实更新索引并保留风险，Pro
  反而漏索引并丢失两家公司风险，Pro 并非稳定更可靠。

## 结论

1. **Pro 更容易遵循当前投研特化 Planner 路由。** 四题中只对 PLAN-02/04 规划，说明 system prompt
   的领域例子确实影响工具选择；但非投研复杂任务仍没有通用路由。
2. **Planner 调用与成功没有正相关。** 两个 0 Planner 任务语义通过，两个 1 Planner 任务失败。
   差异受任务难度影响，不能反向断言 Planner 有害，但足以否定“调用即有效”。
3. **计划时机和覆盖比调用次数更重要。** PLAN-02 写入前规划，后段交付完整；PLAN-04 写完公司页
   才规划，无法防止未读覆盖和风险丢失。
4. **具体来源追溯是跨模型共同盲点。** PLAN-02/04 都把目录或泛化材料类型当成可追溯来源；计划
   也没有把这个公开成功条件纳入步骤。
5. **Pro 的收益不单调且代价明显。** 语义 outcome 小样本增加 1 题，但 token +10.8%、成本
   +19.5%、耗时 2.55 倍；PLAN-04 行为反而弱于 Flash。

## 机制决策与下一步

- 不因本轮 Pro 2/4 就切换默认模型；每题只有 1 次，且 PLAN-04 已显示明显反例。
- 优先实现 required-planner variant：首次 mutation 前必须建立计划，计划需覆盖公开成功条件和禁止
  事项，并在每阶段后更新。
- 对 PLAN-02/04 把“具体来源路径覆盖率”“索引真实落盘”“既有风险保留”设为独立指标，比较
  Flash/Pro 的 optional/required 各至少 3 trials。
- 加 candidate answer validation，拦截“索引未修改却声称已更新”。
- 继续修正题面与 grader 契约：PLAN-02 报告名改为语义发现；PLAN-03 标题正则修复已保留。
