# Planner 复杂任务阶段总结

日期：2026-07-30
范围：PLAN-01～04、Optional Planner 触发、题面与 Prompt 结构、Flash/Pro 模型差异
状态：阶段性结论，尚未完成 Planner 因果验证

## 1. 背景与目标

早期 `planner-experiment-v1` 在 4 个任务、12 次真实模型 trial 中全部成功，但
`update_plan` 调用为 0。原任务大多是线性读取和写入，无法回答“显式 Planner 是否改善复杂任务”。

本轮围绕一个机制假设展开：

> 当任务包含多个依赖阶段、多个环境产物、条件式行动和容易遗漏的成功条件时，显式 Planner
> 可能减少遗漏、无依据完成声明和跨文件不一致。

为避免把“调用了 Planner”误当作成功，所有任务仍以环境最终状态为主要验收，Plan 调用只作为
非必需诊断指标。

## 2. 新增任务与判卷能力

新增 `planner-complex-experiment-v1`（PLAN-01～03），以及单独验证投研场景的
`planner-investment-research-experiment-v1`（PLAN-04）：

| Task | 场景 | 主要复杂度 |
|---|---|---|
| PLAN-01 | 身份服务 V2 迁移 | 条件筛选、服务依赖、部署/回滚顺序、多文件一致性 |
| PLAN-02 | 三家公司季度知识库更新 | 多来源、多公司页、横向报告、索引、可追溯性 |
| PLAN-03 | 支付事故处置 | 证据集合、条件式行动、禁止扩大处置、事故报告 |
| PLAN-04 | 储能逆变器投委会研究 | 三份正式材料、估值计算、旧风险保留、横向报告、索引、具体来源追溯 |

每题使用 fixture 内 pytest 做确定性 outcome 判卷，并新增 `allowed_diff` safety grader，限制 Agent
只能修改题目允许的路径。四个任务均满足 known-bad 失败、Oracle 通过；`raw/` 不参与运行且
继续由全局 forbidden diff 保护。

## 3. 题面演进与实验结果

### 3.1 结构化题面：外部已经提供计划

首版题面用编号步骤明确告诉 Agent 应该读取、更新、生成报告和修改索引。使用
`deepseek-v4-flash`、Optional Planner，每题 1 trial：

| Outcome | Steps | Tool calls | Plan calls | Tokens | Cost |
|---:|---:|---:|---:|---:|---:|
| 3/3（PLAN-03 grader 修正后） | 42 | 39 | 0 | 173,882 | $0.474544 |

三个任务全部完成，但没有 Planner。复盘发现题面本身已经是一份执行计划，模型没有必要再调用
`update_plan`。PLAN-03 原始 summary 的失败是 grader 假阴性：测试错误地从首次出现“回滚”二字
开始比较服务顺序，而不是定位正式回滚章节。修正后冻结环境通过，原始 run 保留。

### 3.2 自然目标题面：只给目标、完成态和约束

第二版移除动作顺序，只保留目标、成功条件和禁止事项。其他条件不变：

| Outcome | Steps | Tool calls | Plan calls | Tokens | Cost |
|---:|---:|---:|---:|---:|---:|
| 1/3 | 48 | 45 | 0 | 210,866 | $0.594422 |

相对结构化题面：steps +14.3%、tool calls +15.4%、tokens +21.3%、cost +25.3%。

- PLAN-02 运行到 23/24 步，完成页面、报告和索引，但遗漏三个公司页的来源路径。
- PLAN-03 没有读取已经在目录中看到的发布记录，报告遗漏 09:40 事件和对应证据路径。

自然题面成功暴露了长链路状态丢失和过早收尾，但当前 Optional Planner 仍未触发。

### 3.3 PLAN-02 极简题面：只保留一句开放目标

题面缩减为：

> 使用 sources/2026Q3/ 中三家半导体公司的正式季度材料，把知识库更新到 2026Q3，并发布一份可追溯的横向比较结果。

Flash 结果：13 steps、12 tool calls、0 Plan、49,301 tokens、$0.140632。模型更新三个公司页后
直接回答，没有创建报告、没有更新索引、没有写来源路径，却声称“索引已同步、横向对比完成”，
并给出一个实际不存在的报告路径。

这次运行是开放目标理解 probe，不是公平的正式 outcome eval：原 grader 仍要求固定文件名、原风险
保留和公司页来源，其中部分要求不再由极简题面明确公开。但“未写报告却声称已经发布”不依赖隐藏
grader，属于真实的无依据完成声明。

### 3.4 同题换模型：Flash vs Pro

保持极简题面和全部运行条件不变，仅把模型替换为 `deepseek-v4-pro`：

| Metric | Flash | Pro |
|---|---:|---:|
| steps | 13 | 16 |
| tool calls | 12 | 15 |
| plan calls | 0 | 1 |
| tokens | 49,301 | 72,773 |
| cost | $0.140632 | $0.216366 |
| duration | 46.58s | 143.99s |

Pro 在三个公司页写完后的第 12 步创建计划：公司页更新 completed、横向报告 in_progress、索引
pending。随后它真实创建报告、更新索引，并在报告中列出三个来源；相较 Flash，后半段交付明显更
完整。

但计划创建得太晚。Pro 未先读取星河芯片旧页便覆盖写入，编造 2026Q2 营收、毛利率和客户，
替换原风险提示，并用虚构历史值计算环比。它使用了题面允许的合理报告名，但旧 grader 和
`allowed_diff` 仍只接受固定旧文件名，因此 raw grade 中混合了 grader 不对齐与真实事实错误。

### 3.5 通用复杂度 Prompt：Flash 仍不触发

曾把 system prompt 的 Planner 路由从“多轮投研、多公司对比”改为多交付物、多文件、依赖、条件
行动、证据覆盖和多成功约束等通用结构。PLAN-01～03 每题 1 trial：

| Outcome | Steps | Tool calls | Plan calls | Tokens | Cost |
|---:|---:|---:|---:|---:|---:|
| 1/3 | 39 | 36 | 0 | 159,683 | $0.472316 |

更通用的措辞没有让 Flash 调用 Planner，也没有改善 outcome；相对各题当前题面的最近 baseline，
tokens +6.7%、cost +9.3%、duration +7.9%。该候选不保留，生产 system prompt 已恢复。这个负结果
说明 Optional 路由问题不能只靠扩展示例解决。

### 3.6 PLAN-04：更贴合投研，Flash 触发仍有波动

PLAN-04 只给投委会研究目标、完成态和约束，不给步骤；报告名和排版使用语义 grader，避免隐藏固定
路径。对 Agent 可见条件相同的两次 Flash 运行中：

| Run | Outcome | Steps | Tools | Plan calls | Tokens | Cost |
|---|---:|---:|---:|---:|---:|---:|
| grader pilot | fail | 17 | 16 | 0 | 86,756 | $0.243222 |
| 正式 trial | fail | 18 | 17 | 1 | 92,054 | $0.275668 |

正式 trial 在首次写入前建立计划，随后真实完成报告和索引；0 Planner trial 漏索引却声称完成。
但两次都只引用泛化目录，没有把关键数字落到三份具体材料路径，因此真实 outcome 均失败。Flash
temperature=0 下 Planner 触发仍为 0/1，不能视为稳定路由。

### 3.7 Pro 跑 PLAN-01～04：只在投研题规划

保持四题、工具、system prompt、temperature 和预算不变，只覆盖模型为 `deepseek-v4-pro`：

| Task | Raw outcome | 语义 outcome | Plan calls | Plan 时机 |
|---|---:|---:|---:|---|
| PLAN-01 | pass | pass | 0 | — |
| PLAN-02 | fail | fail | 1 | 全部读取后、首次写入前 |
| PLAN-03 | fail | pass | 0 | — |
| PLAN-04 | fail | fail | 1 | 三份公司页写完后 |

PLAN-03 的 raw failure 是“失败回滚顺序”标题被过窄正则误判；修复后 known-bad 仍失败、Oracle 通过，
原 trace mutation 重放 2/2 通过。Pro 的语义 outcome 为 2/4，Planner 只在 PLAN-02/04 两道多公司
投研题触发，与当前 system prompt 的领域特化描述一致。

PLAN-02 的 Plan 在写入前创建，报告和索引完整落盘且没有再次编造历史数据，但仍漏具体来源路径。
PLAN-04 的 Plan 太晚：模型未读两份旧档案便覆盖，丢失原风险；随后漏写索引却声称已更新。两次 Plan
都没有阶段更新。

相对当前四题最近 Flash trial，Pro 语义 outcome 1/4→2/4、plan calls 1→2，但 tokens +10.8%、
cost +19.5%、duration 2.55x。每题只有 1 trial，且 PLAN-04 反而退化，不支持切换默认模型。

## 4. 当前可以成立的结论

1. **复杂任务集现在有区分度。** 移除预制步骤后，裸循环从 3/3 降为 1/3，并增加步骤和成本。
2. **Planner 路由同时受模型、领域语境和运行波动影响。** Pro 只在两道多公司投研题规划；Flash 在
   相同 PLAN-04 条件下出现 0/1 次。不能把触发问题只归因于工具注册或题面结构。
3. **当前 Optional Planner 是领域特化路由，不是通用复杂度路由。** PLAN-01/03 的多文件、依赖和
   条件行动没有触发 Pro；而把 system prompt 改成通用复杂度措辞，也没有让 Flash 触发。
4. **Plan 调用不是充分成功指标，也不是必要条件。** Pro 的两个 0 Planner 任务语义通过，两个
   1 Planner 任务失败；任务难度不同，不能断言 Planner 有害，但足以否定“调用即有效”。
5. **计划时机、成功条件覆盖和更新质量比调用次数更重要。** 写入前规划的 PLAN-02 后段交付较完整；
   写完公司页才规划的 PLAN-04 无法防止未读覆盖。所有 Optional Plan 都没有持续更新。
6. **具体来源追溯是跨模型共同盲点。** PLAN-02/04 中 Flash 和 Pro 都容易把目录或材料类型当作
   “可追溯来源”，计划也没有主动展开这一公开成功条件。
7. **环境 outcome 必须优先。** 多次出现索引或配置未修改、最终回答却声称完成；只看 answer 会漏掉
   风险丢失、事实编造和未落盘产物。
8. **Pilot 必须先于正式多 trial。** 本轮累计发现固定报告名、固定表格方向和回滚标题正则等 grader
   假阴性；若直接汇总 raw success 会得到错误结论。

## 5. 尚不能成立的结论

- 不能声称 Planner 已提高成功率；目前没有同模型、同题面的 required-planner 对照。
- 不能声称 Pro 稳定优于 Flash；四题仍只有单次方向性对照，PLAN-04 上 Pro 反而弱于 Flash，且成本
  和延迟显著更高。
- 不能用当前极简题面的 raw grade 比较模型，因为部分 grader 要求已经从题面中移除。
- 不能用“有 Plan trial 后段更完整”证明 Planner 因果收益；模型运行本身有波动，且计划常发生在
  部分工作完成之后。
- 不能因为通用 Prompt 单次失败就断言 Prompt 永远无效；目前只能判断该候选没有获得保留证据。

## 6. 待解决问题

### P0：Eval 契约与 grader 对齐

1. 区分两类任务：
   - 正式 Planner outcome task：公开全部成功条件，但不提供执行顺序；
   - 开放目标 capability probe：只给意图，grader 检查语义结果，不隐藏固定文件名。
2. PLAN-02 的报告 grader 应验证“存在一个被索引、包含三家公司和来源的 Q3 横向报告”，而不是
   固定唯一文件名；事实保真、来源和禁止修改仍是硬门槛。
3. PLAN-04 已采用语义报告发现和等价比率表达，可作为 PLAN-02 修正参考。PLAN-03 回滚标题正则
   假阴性已修复并完成 known-bad/Oracle/trace mutation 重放验证。
4. TaskSpec 应记录题面版本/hash，避免不同 instruction 的 run 被汇总为同一个 task 版本。

### P0：验证 Planner 机制本身

1. 保持自然目标题面不变，增加 required-planner variant，在首次 mutation 前建立计划。
2. Plan 至少覆盖所有成功条件、禁止事项和关键依赖；不能只罗列工具动作。
3. 同一模型运行 baseline / optional / required，每题先 3 trials；PLAN-02/04 单独记录具体来源路径
   覆盖率、索引落盘和旧风险保留。
4. 单独记录 plan 创建时机、覆盖的成功条件、更新次数、实际行为偏离和 outcome recovery。

### P1：通用复杂度路由

单次通用复杂度 Prompt 候选已经实验：Flash 0/3 Planner、outcome 无改善、成本上升，因此未保留。
required-planner 尚未证明收益前，不继续堆叠 Optional 路由措辞。若以后重试 Prompt 路由，应冻结
题面和 grader，至少 3 trials，并同时测简单任务误触发率。

### P1：可信完成与候选答案验证

1. `answer` 应是候选完成动作，而不是直接把 run 标记 completed。
2. 对写入任务确定性检查声明的 artifact 是否存在、索引是否真实更新、必要来源是否落盘。
3. 失败反馈模型并允许有限 revision；grader 仍作为最终外部裁判。
4. 解决 summary 声称将读取某文件、实际 tool call 却没有执行的行为—状态不一致。
5. PLAN-02/04 已提供直接驱动案例：报告或索引未落盘却自报完成；PLAN-04 Pro 还出现 invalid action
   后直接 answer，未恢复计划中的 pending 索引步骤。

### P1：事实保真与写入安全

1. 写已有页面前由运行时或工具策略保证先读，不能只依赖 prompt。
2. ToolResult 增加 mutation、artifact hash 和 evidence 引用；报告中的数字应能追溯到本轮 observation。
3. 对覆盖写增加原内容保留/丢失检测，拦截 Pro 式编造历史数据和替换风险提示。
4. 区分“引用了来源目录”和“关键 claim 绑定到具体文件”；PLAN-02/04 表明模型会把前者误认为已经
   可追溯。

### P2：可比较性与 Trace

1. Eval 与产品目前分别走非流式和流式模型请求；应明确它是否属于固定实验条件及产品外推限制。
2. manifest/trace 需要保存 system prompt、Tool Spec、模型请求形态、prompt hash 和 task version。
3. 价格、延迟和 token 指标需按模型/provider 明确计价，避免把模型差异简化为成功率。

## 7. 推荐下一步顺序

```text
修正 PLAN-02 正式 grader 与开放 probe 的边界
→ manifest/trace 固化 system prompt、Tool Spec、task version 与 hash
→ 实现首次 mutation 前 required-planner + 成功条件覆盖检查
→ Flash/Pro 在 PLAN-01～04 跑 optional / required 各 3 trials
→ 确认 Planner 是否恢复具体来源、旧风险、索引和证据覆盖失败
→ 接候选答案 validation 与有限 revision
→ 有因果收益后再决定是否重试通用 Optional 路由 Prompt
```

在 required-planner 证明 outcome 收益之前，不扩大生产 Planner 路由，也不把哑工具升级为复杂状态机。

## 9. 2026-07-31 Flash 正式版别名复跑

在 system prompt、题面、工具、grader、temperature 和预算不变的条件下，使用
`deepseek-v4-flash` 对 PLAN-01～04 各并发运行 1 trial。Provider 未返回可验证版本号，因此本轮只
能视为相同模型别名下的新行为样本。

Raw outcome 为 2/4；修复 PLAN-01“从正文首次出现回滚开始截取”的 grader 假阴性后，人工复核语义
outcome 为 3/4。Planner 在 PLAN-01/02/04 分别调用 4/3/3 次，PLAN-03 为 0，总计 10 次；相较旧
Flash 最近四题仅 1 次、Pro 仅 2 次且都没有更新，路由和状态维护均发生明显变化。

PLAN-04 在首次写入前完成材料、旧档案、索引和测试的收集计划，最终首次同时满足具体来源、旧风险、
计算、报告和索引，是当前最强的 Planner 正向过程证据。PLAN-02 虽由计划推动补齐报告和索引，仍因
计划没有把“可追溯”展开为逐公司具体路径而失败。PLAN-03 无 Planner 通过，说明显式规划并非所有
复杂任务的必要条件。

本轮仍不能证明 Planner 因果价值：模型后端本身可能同时变化，每题只有 1 trial，也没有同后端下
disabled / optional / required 对照。成本同时升至 78 steps、448,941 tokens、$1.541422；PLAN-01
四次计划更新后正好用满 20 steps。下一步优先做交错多 trial 对照、最终环境验证和 Planner 预算
语义，不继续仅凭 Optional 触发次数调整 Prompt。
